# Work 프로젝트 실행 Current Router

```text
WORK_PROJECT_EXECUTION_CURRENT_ROUTER
THIN_ROUTER_NOT_SECOND_CANON
PROJECT_CANON_AND_ACTUAL_IMPLEMENTATION_FIRST
CURRENT_BASE_OWNER_WINS_ON_DRIFT
FIVE_STAGE_VERTICAL_SLICE_FLOW_REQUIRED
MACRO_STAGE_IS_NOT_WORK_MODE
GAME_PROJECT_ONLY
NON_GAME_PROJECT_NOT_APPLICABLE
```

> 프로젝트 사실과 전문 절차를 복제하지 않는 얇은 진입점이다. 게임 프로젝트 공용 macro flow는 5단계이며, Project의 `PLAN / BUILD / REVIEW` 같은 Work Mode는 각 단계 안의 수행 방식이다.

## 1. 권위와 owner routing

```text
사용자의 최신 명시 지시
→ Project AGENTS / Active Context / 승인 Decision
→ Project GitHub·Notion current canon
→ actual code/data/Scene/Resource/asset/test/runtime evidence
→ Project가 채택한 current Base owner
→ Base latest completed main
→ 과거 채팅·Memory·handoff
```

```text
WORK_CODEX_MINIMUM_TRANSITION_STARTER_PROMPT.md
WORK_PROJECT_START_CANON_CHECKLIST.md
WORK_CODEX_MINIMUM_TRANSITION_VERTICAL_SLICE_PROFILE.md
WORK_PROJECT_LOCAL_VISUAL_ASSET_DELIVERY_PROFILE.md
WORK_EXECUTION_EVIDENCE_IDENTITY_INTEGRITY.md
```

과거 대화와 Memory는 discovery 후보일 뿐이다. 충돌하면 `CONTEXT_DRIFT_RECHECK_REQUIRED`로 되돌린다.

## 2. 시작 전 정본 교정

새 기획·production·Codex mutation 전에 `WORK_PROJECT_START_CANON_CHECKLIST.md`로 핵심 재미/player promise, core/support systems와 actual consumer, current stage/active Slice, 구현·test·Visual·Audio, SWOT, blocker/dependency/protected scope, remaining work/order, stale/conflict/missing canon을 확인한다.

승인 범위의 작은 정본 결함은 먼저 교정하고 GitHub structured / Notion human canon을 readback한다. Core·주요 UX·경제·서사·Art Direction처럼 제품 의미가 바뀌는 결정만 사용자 결정으로 남긴다.

## 3. 게임 프로젝트 Work 5단계 macro flow

상세 Gate는 `WORK_CODEX_MINIMUM_TRANSITION_VERTICAL_SLICE_PROFILE.md`가 소유한다. `MINIMIZE_WORK_CODEX_TRANSITIONS`는 단계를 합친다는 뜻이 아니라 **1~3단계를 Work에서 닫고 4단계 Codex를 한 구현 window로 묶는다**는 뜻이다.

### 1단계 — 기획

```text
STAGE_1_PLANNING
USER_COLLABORATIVE_CORE_PLANNING_REQUIRED
GRILL_ME_FOR_MATERIAL_CORE_DECISIONS
DECISION_RELEVANT_BENCHMARK_REQUIRED
THREE_MATERIALLY_DISTINCT_APPROACHES
ADOPT / ADAPT / REJECT
```

Project canon·실제 구현·승인 자산·Base reuse를 먼저 읽는다. 아직 승인되지 않은 player promise, 핵심 행동/선택·trade-off, reward/failure learning, 감정·기억·첫인상, 세일즈포인트, Slice 가설/acceptance처럼 제품 의미를 바꾸는 항목은 current Grill Me + decision-relevant benchmark로 사용자와 함께 닫는다. 이미 확인 가능한 사실·구현 세부·가역적 초기값은 다시 묻지 않는다.

### 2단계 — 검수

```text
STAGE_2_PRE_PRODUCTION_REVIEW
PRE_PRODUCTION_REVIEW_CLEAN
NO_ASSET_PRODUCTION_BEFORE_REVIEW_CLEAN
NO_CODEX_PRODUCT_MUTATION_BEFORE_REVIEW_CLEAN
```

1단계 계약을 canon/implementation drift, Existing Solution First, benchmark applicability, player choice, UI/UX, data/state/save, actual consumer, rights, acceptance, QA/evidence ceiling 관점에서 검수·교정한다. 제품 의미 변경은 1단계로 되돌리고 `PRE_PRODUCTION_REVIEW_CLEAN` 전에는 production asset이나 Codex product mutation을 시작하지 않는다.

### 3단계 — 이미지·요소 생성

```text
STAGE_3_ASSET_AND_ELEMENT_PRODUCTION
ACTUAL_CONSUMER_REQUIRED
WORK_PRODUCTION_INPUT_PACKET
READY_FOR_SINGLE_CODEX_WINDOW
```

검수된 current Slice의 실제 consumer가 있는 Visual·Audio·UI source·VFX·runtime-consumed data/content만 제작한다. Project/host 이미지 승인 Gate는 유지하고, durable locator·provenance·rights·format/import·acceptance까지 닫아 Codex 입력 packet으로 만든다.

### 4단계 — 구현(Codex) + machine closure

```text
STAGE_4_CODEX_IMPLEMENTATION_AND_MACHINE_CLOSURE
CODEX_SINGLE_IMPLEMENTATION_WINDOW
WORK_FINAL_EVIDENCE_REVIEW_IS_STAGE4_CLOSEOUT
WORK_FINAL_EVIDENCE_REVIEW_BEFORE_USER_VALIDATION
```

Codex가 actual code·Scene·Resource·runtime wiring·test·build를 한 window에서 처리한다. 반환 뒤 Work의 diff/runtime/evidence 검수, correction, canon sync, exact-head CI, safe merge, post-merge readback은 Stage 4 closeout이다.

```text
AUTOMATED_VERTICAL_SLICE_READY
READY_FOR_USER_VERTICAL_SLICE_VALIDATION
HUMAN_USABILITY_EVIDENCE: NOT_RUN
PLAYER_EXPERIENCE_EVIDENCE: NOT_RUN
```

machine-executable current-Slice required work가 0이고 exact build/launch route가 준비된 상태이지 최종 완료가 아니다.

### 5단계 — 사용자 검증

```text
STAGE_5_USER_VALIDATION
ACTUAL_USER_PLAY_REQUIRED
AUTOMATED_VERTICAL_SLICE_READY != VERTICAL_SLICE_VALIDATED_COMPLETE
NEXT_SLICE_REQUIRES_STAGE5_DECISION
```

사용자가 exact build/scene을 실제 플레이하고 조작 이해, meaningful choice, feedback/reward/failure learning, UI/Visual/Audio 지각, 감정·기억·첫인상·세일즈포인트를 검증한다. 실제 play evidence와 `EXPAND / REWORK / REPEAT_SLICE / HOLD / STOP` Decision Gate가 기록·readback된 뒤에만 `VERTICAL_SLICE_VALIDATED_COMPLETE`를 사용한다.

## 4. Project-local Visual opt-in

```text
WORK_PROJECT_LOCAL_VISUAL_ASSET_DELIVERY_PROFILE.md
PROJECT_LOCAL_VISUAL_BINARY_FIRST
NOTION_VISUAL_STRUCTURE_REFERENCE_ONLY
NO_NOTION_BINARY_UPLOAD_REQUIRED
```

Project-local candidate → SHA/provenance/rights → `PROJECT_ASSET_APPROVED` → tracked asset + `ASSET_MANIFEST` → commit/push/remote readback → Codex locator → Godot actual consumer/runtime evidence 순으로 승격한다. Project별 binary owner와 host approval Gate가 우선하며 실제로 하지 않은 Notion binary upload를 주장하지 않는다.

## 5. Evidence identity와 안전 자동화

```text
WORK_EXECUTION_EVIDENCE_IDENTITY_INTEGRITY.md
product baseline SHA != documentation/router sync SHA
TEST_LOGIC_PASS != CI_GATE_PASS
LOCAL_VISUAL_CANDIDATE != PROJECT_ASSET_APPROVED != RUNTIME_PROMOTED
machine QA != Human usability != Player Experience
```

```text
safe fetch / ff-only pull
→ current-task branch commit/push/readback
→ exact-head required checks / squash merge
→ post-merge main readback
→ adopted GUT/Hera or evidence-equivalent runtime/screen/build QA
→ current Slice machine-executable required work = 0
→ 최소 5회 full-scope adversarial review
→ blocking finding 0
```

금지: direct main / force / blind reset·clean·rebase / 다른 open PR takeover / 새 유료 비용 / 공개 Release·스토어 게시 / 권한·보안 우회.

`AUTOMATED_VERTICAL_SLICE_READY`는 Stage 5 입장 조건이며 `VERTICAL_SLICE_VALIDATED_COMPLETE`가 아니다. 사용자 검증 전에는 다음 Slice로 자동 진입하지 않는다.
