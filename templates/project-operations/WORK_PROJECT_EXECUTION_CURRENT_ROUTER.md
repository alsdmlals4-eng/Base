# Work 프로젝트 실행 Current Router

```text
WORK_PROJECT_EXECUTION_CURRENT_ROUTER
THIN_ROUTER_NOT_SECOND_CANON
PROJECT_CANON_AND_ACTUAL_IMPLEMENTATION_FIRST
CURRENT_BASE_OWNER_WINS_ON_DRIFT
FIVE_PHASE_INTERFACE_FIRST
```

> 프로젝트 사실·세부 절차를 복제하지 않고 현재 owner를 연결하는 얇은 진입점이다.

## 1. 권위와 로드 순서

```text
사용자의 최신 명시 지시
→ Project AGENTS / Active Context / 승인 Decision
→ Project GitHub·Notion 분야별 current canon
→ 실제 code/data/Scene/Resource/asset/test/runtime evidence
→ Project가 채택한 current Base owner
→ Base latest completed main
→ 과거 채팅·Memory·handoff
```

```text
1. exact Project identity / GitHub / Notion / actual implementation
2. Base latest main / root AGENTS / current Skill Registry inventory
3. WORK_CODEX_MINIMUM_TRANSITION_STARTER_PROMPT.md
4. WORK_PROJECT_START_CANON_CHECKLIST.md
5. WORK_FIVE_PHASE_VERTICAL_SLICE_EXECUTION_CONTRACT.md
6. WORK_CODEX_MINIMUM_TRANSITION_VERTICAL_SLICE_PROFILE.md
7. WORK_EXECUTION_EVIDENCE_IDENTITY_INTEGRITY.md
8. trigger되는 current Base·Project 전문 owner
```

과거 대화와 Memory는 discovery 후보일 뿐이다. 충돌하면 `CONTEXT_DRIFT_RECHECK_REQUIRED`로 되돌린다.

## 2. 시작 전 정본 교정

새 기획·production·Codex mutation 전에 `WORK_PROJECT_START_CANON_CHECKLIST.md`로 확인한다.

```text
핵심 재미 / player promise / core·session·meta loop
핵심·지원 시스템 / actual consumer
meaningful choice / reward / failure learning
evidence-based SWOT
current stage / active Slice / accepted frontier
구현·test·Visual·Audio 상태
남은 required work / dependency / protected scope
stale·duplicate·conflict·missing canon
GitHub structured / Notion human canon readback
```

승인 범위의 작은 정본 결함은 먼저 교정한다. Core·주요 UX·경제·서사·Art Direction처럼 제품 의미가 바뀌는 결정은 Phase 1 사용자 공동기획으로 보낸다.

## 3. 사용자 Work 5단계 macro interface

상세 phase transition은 `WORK_FIVE_PHASE_VERTICAL_SLICE_EXECUTION_CONTRACT.md`가 소유한다.

```text
PHASE_1_PLANNING_CO_DESIGN
→ PHASE_2_PREPRODUCTION_REVIEW
→ PHASE_3_WORK_INGAME_ELEMENT_PRODUCTION
→ PHASE_4_CODEX_IMPLEMENTATION_AND_MACHINE_CLOSEOUT
→ PHASE_5_USER_VERTICAL_SLICE_VALIDATION
```

```text
1. 기획: current canon·Grill Me·benchmark·3개 실질 대안으로 핵심 제품 의미를 사용자와 공동 확정
2. 검수: 기획/scope/reuse/feasibility/UI·Data/consumer/rights/acceptance를 구현 전 공격·교정
3. 이미지&요소 생성: 검수된 actual-consumer Visual·Audio·UI·Data·VFX 등 Work 입력 제작
4. 구현(Codex): single implementation window + machine QA + Work final implementation review·merge/readback
5. 사용자 검증: exact build 실제 플레이 + Human/Player evidence + next decision
```

Project의 `PLAN / BUILD / REVIEW`, DoR, Task, Decision, package candidate 같은 native state는 rename하지 않고 `FIVE_PHASE_PROJECT_MAPPING`으로 의미를 매핑한다.

## 4. Work↔Codex 최소 전환

`WORK_CODEX_MINIMUM_TRANSITION_VERTICAL_SLICE_PROFILE.md`는 packet·routine approval·fallback·machine QA·merge 세부를 소유한다. 그 파일의 Stage A/B/C 표현은 **5단계를 대체하는 macro flow가 아니라 내부 최소전환 grouping**으로만 해석한다.

```text
Phase 1~3 Work에서 닫기
→ WORK_PRODUCTION_INPUT_PACKET
→ CODEX_SINGLE_IMPLEMENTATION_WINDOW
→ actual code/Scene/Resource/runtime/test/build
→ CONSOLIDATED_RETURN_PACKET
→ Phase 4 Work final implementation review·교정·canon sync·merge/readback
→ AUTOMATED_VERTICAL_SLICE_READY
→ READY_FOR_USER_VERTICAL_SLICE_VALIDATION
→ Phase 5 actual user play
```

작은 누락마다 Work↔Codex를 왕복하지 않는다.

## 5. Project-local Visual opt-in

사용자가 이미지 binary를 각 프로젝트가 소유하도록 명시하면 함께 적용한다.

```text
WORK_PROJECT_LOCAL_VISUAL_ASSET_DELIVERY_PROFILE.md
PROJECT_LOCAL_VISUAL_BINARY_FIRST
NOTION_VISUAL_STRUCTURE_REFERENCE_ONLY
NO_NOTION_BINARY_UPLOAD_REQUIRED
```

```text
Notion 구조·Art Direction fresh-read
→ project-local candidate
→ format/dimensions/SHA-256/provenance/rights readback
→ PROJECT_ASSET_APPROVED
→ tracked project asset + ASSET_MANIFEST
→ commit/push/remote readback
→ Codex project-relative locator
→ runtime consumer evidence
```

actual consumer 없는 설명 이미지를 production asset으로 만들지 않는다. Notion text/status를 수정했으면 readback하며 실제로 하지 않은 binary upload를 주장하지 않는다.

## 6. Evidence identity와 완료 경계

`WORK_EXECUTION_EVIDENCE_IDENTITY_INTEGRITY.md`로 세부 identity를 분리한다.

```text
product baseline SHA != documentation/router sync SHA
current validation HEAD != build/runtime candidate HEAD
TEST_LOGIC_PASS != CI_GATE_PASS
LOCAL_VISUAL_CANDIDATE != PROJECT_ASSET_APPROVED != RUNTIME_PROMOTED
machine QA != Human usability != Player Experience
```

```text
AUTOMATED_VERTICAL_SLICE_READY
READY_FOR_USER_VERTICAL_SLICE_VALIDATION
HUMAN_USABILITY_EVIDENCE: NOT_RUN
PLAYER_EXPERIENCE_EVIDENCE: NOT_RUN
AUTOMATED_VERTICAL_SLICE_READY != USER_VALIDATED_VERTICAL_SLICE
```

사용자가 exact build를 실제 플레이하고 Phase 5 evidence·next decision·Canonical Reflection After Play가 Project canon에 기록·readback되기 전에는 `USER_VALIDATED_VERTICAL_SLICE`를 주장하지 않는다.

## 7. 안전 자동화와 clean exit

```text
safe fetch / ff-only pull
→ current-task branch commit/push/readback
→ exact-head required checks / squash merge
→ post-merge main readback
→ adopted GUT/Hera or evidence-equivalent runtime/screen/build QA
→ current Slice machine-executable required work = 0
→ 최소 5회 full-scope adversarial review
→ blocking finding 0
```

금지: direct main / force push / blind stash·reset·clean·rebase / 다른 open PR takeover / 새 유료 비용 / 공개 Release·스토어 게시 / 권한·보안 우회.

사용자 검증 전에는 다음 Slice로 자동 진입하지 않는다.

## 8. 비게임/Project-specific 값

비게임/서사 프로젝트는 5단계 업무 분리 원칙을 domain production에 adapt하고 Godot/GUT/Hera/game-runtime evidence만 `NOT_APPLICABLE`로 둔다. 게임 Vertical Slice 완료를 비게임 산출물에 오용하지 않는다.

프로젝트명·캐릭터·세계관·특정 PR/Issue/Task/Decision·SHA·경로·해상도·HUD·palette·Art Style·완료 목록·우선순위·현재 phase는 exact Project canon에서 fresh-read하며 이 router에 고정하지 않는다.
