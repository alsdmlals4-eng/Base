# 재미 가설을 효과·비주얼·UI 명세로 연결하기

`EXPERIENCE_TO_PRESENTATION_CONTRACT` — 기능을 정립할 때 "화려하게 / 타격감 있게 / 직관적으로"를 구현 가능한 행동·상태·표현·관찰 질문으로 바꾼다. 새 감독 Skill·디자인 시스템·게임 규칙의 정본이 아니라 기존 UX/UI owner의 조건부 작성 가이드다.

## 1. 적용과 책임

- 출발점은 [재미 검증 생명주기](../../analyzing-and-refining-game-concepts/references/concept-evidence-and-gates.md#fun-verification-lifecycle)의 승인된 경험 가설이다. 효과·아트·UI 중 바뀌는 부분만 사용한다. L1은 기존 Brief/Decision에 짧게, L2는 기존 전문 정본 또는 기능 Spec에 연결한다. L0 기계 수정은 이유 있는 비적용, 유효한 같은 조건의 근거는 `REUSED_EVIDENCE`다.
- `GAMEPLAY_EFFECT`는 피해·회복·버프·진행 변경 같은 **규칙 효과**다. 발동 조건, 대상, 값/계산식, 지속·만료, 중첩·갱신·상한, 비용·실패·면역을 기존 시스템/데이터 owner에서 정한다. 해당하지 않는 항목은 이유와 함께 생략한다.
- `PRESENTATION_EFFECT`는 VFX·모션·소리·카메라 등 **표현 효과**다. 규칙 효과의 원인·예고·확정 결과를 전달하거나 감각·세계관·표현의 만족을 만든다. 같은 `requirement_id`로 연결하되 표시 코드가 피해·보상·저장을 재계산하지 않는다.
- 기능 Spec의 Experience Intent, `GAME_UX_UI_SYSTEM`의 상태·피드백·Godot·검증 절, Art/Visual Bible과 Asset Catalog를 `source_id + path + section`으로 참조한다. `GAME_FEATURE_DESIGN_SPEC`에 전문 분야 내용을 다시 복제하지 않는다. 실행 결과는 `FEATURE_SPEC_TRACEABILITY_PACKET` 또는 기존 validation owner로 연결한다.
- 핵심 경험·정보 공개 범위·경제·아트 방향·주요 UX를 바꾸는 결정은 `USER_DECISION_REQUIRED`다. 구현 방법의 안전한 구체화는 기존 승인 범위에서 계속한다. 모든 게임을 전투·속도·반복 보상 중심으로 만들지 않는다.

## 2. 한 기능을 정립하는 최소 작성 칸

아래는 기존 정본의 빈칸을 찾는 질문이다. 새 JSON schema나 별도 카드 파일을 강제하지 않는다. 필드 이름은 프로젝트의 기존 키에 매핑한다.

| 작성 칸 | 구체적으로 남길 내용 | 모호한 지시를 바꾸는 예 |
|---|---|---|
| 경험·원본 | `requirement_id`, 승인 원본, 어떤 상황의 어떤 이해·감정·선택·표현을 지원하는가 | "재미있게" → "내 방어로 피해가 줄었다는 원인과 성취를 알린다" |
| 규칙·권위 | `state_owner`, 입력/사건, 허용 조건, 규칙 결과의 source, 아직 가설인 부분 | "방패 효과" → "판정된 방어 결과를 읽어 표시; 감소량은 전투 owner 값" |
| 정보·시선 | 누가 무엇을 언제 알아야 하는가; 먼저 볼 것과 가리면 안 되는 것; 공개하지 않을 정보 | "눈에 띄게" → "현재 대상과 예고를 보존하고 결과 위치만 강조" |
| 시각 언어 | 승인 아트 방향, 형태·실루엣·명암·색의 역할, 질감, 실제 표시 크기·배경·주변 자산과 일관성 | "고급스럽게" → "기존 인장 형태를 재사용하고 선택/잠금 표식을 구분" |
| 상태·입력 | 필요한 상태, 진입/해제, 동시 상태 우선순위, 포인터·키보드·패드·터치 중 지원 경로, 취소·복귀 | "버튼 반짝임" → "포커스와 선택을 구분하고 비활성 이유를 같은 입력으로 확인" |
| 시간·강도 | 예고/접수/대기/확정/잔상 시점, 반복 빈도, 동시 발생, 우선순위, 중단·즉시 완료·정리 | "강하게 터짐" → "치명적 위험 신호는 보존하고 겹치는 축하 잔상은 축소" |
| 자산·재사용 | 기존 후보·승인 자산 ID, 필요한 상태군, 규격·투명도·pivot/여백, 문자 분리, 제작/권리 상태 | "아이콘 제작" → "현재 아이콘 재사용 가능 여부와 실제 슬롯부터 확인" |
| 구현 연결 | `runtime_consumer`, Scene/Node/Resource/Script, 데이터 입력·Signal 출력, 설정·저장·수명, 통합·실패 경로 | 아직 없는 경로는 `PLANNED`; 설계 경로를 구현 증거로 세지 않음 |
| 판정·반증 | 대표 구간, baseline/후보, 기계·실행·사람별 질문, 실패·중단 기준, `counterevidence`, 다음 결정 | "만족도 높음" → "원인을 설명하는가; 결과를 봤지만 지루하다는 반응도 기록" |

작은 변경은 **목적 → 필요한 상태/표현 → 실제 consumer → 확인 방법**의 짧은 문장으로 위 내용을 참조해도 된다. 경험과 관계없는 필드까지 채우느라 기능 작업을 멈추지 않는다.

## 3. 효과: 의미·시간·강도를 나눠 정한다

```text
조건/사건 확인 → 필요할 때 예고 → 사용자 입력 접수 → 규칙 처리/실제 대기
→ 확정 결과 → 시각·음향·촉각 표현 → 다음 입력 또는 기존 흐름으로 복귀
```

**예고는 미래에 대한 정보, 접수는 입력 확인, 성공은 확정 결과**다. 접수 모션만 재생됐는데 결제·피해·보상 성공처럼 표현하지 않는다. 즉시 끝나는 로컬 처리에 가짜 로딩·필수 대기 연출을 추가하지 않는다.

| 용도 | 효과에서 정할 것 | 반례·실패 질문 |
|---|---|---|
| 행동 접수 | 대상·입력 위치의 작은 반응; 처리 중 여부와 취소 가능성 | 클릭 효과만 있고 실제 요청이 누락됐는가? |
| 위험 예고 | 이미 공개 가능한 대상·방향·범위·시점, 대비 행동에 필요한 신호 | 장식 범위와 실제 판정이 다른가? 숨은 적·정답을 누설하는가? |
| 결과·타격·회복 | 실제 결과의 발생 위치·종류·크기/중요도, 실패/면역/빗나감과 구분 | 효과는 성공인데 상태는 실패인가? 가독성을 가리는가? |
| 보상·해금 | 무엇 때문에 무엇을 얻었고 어디에 반영됐는지, 재확인 위치 | 매번 긴 축하로 다음 선택을 막는가? 희귀도/확률을 거짓 암시하는가? |
| 분위기·감각 | 세계관·재료감·정서에 기여하는 질감/움직임/소리와 허용 강도 | 기능 정보가 없어도 경험 가치는 있을 수 있다. 다만 핵심 판단·읽기와 충돌하는가? |

강도는 기존 `routine / confirming / warning / reward / critical` 분류에 매핑한다. 중요도와 반복 빈도를 함께 보고 색·크기·불투명도·모션·음량을 모두 최대로 올리지 않는다. 동시 효과의 숨김·합치기·우선권과 핵심 신호 보존을 정한다. duration/easing/음량/동시 수는 **프로젝트 검증값 또는 HYPOTHESIS**이며 보편 ms·FPS·효과 개수를 Base 합격선으로 만들지 않는다.

중단·장면 종료·빠른 재입력 때 이전 연출을 정리하고 권위 상태에서 표시를 복구한다. **동일 거래/동일 결과 이벤트**의 중복 재생이 비용·보상을 중복 적용하지 않아야 한다. 정상적으로 구분되는 연속 공격까지 하나로 합치라는 뜻은 아니다. hit-stop·슬로모션·입력 잠금이 실제 판정 시간이나 조작 의미를 바꾸면 단순 장식이 아니라 게임플레이 설계 변경으로 분류한다.

## 4. 비주얼: 정체성·구별·제작성까지 확인한다

[기존 Art Guide](../../../docs/knowledge/game-development/ART_DIRECTION_AND_ASSET_PLANNING_GUIDE.md)의 Visual Requirement Gate를 재사용한다. 새 스타일·캐릭터·아이콘을 자동 확정하지 않는다.

| 대상 | 설계할 구분 | 실제 소비 크기에서 확인할 것 |
|---|---|---|
| 캐릭터·적·오브젝트 | 역할·방향·상태를 드러내는 실루엣; 유지할 상징과 바꿀 수 있는 부분 | 배경·다른 개체·피격 효과와 겹쳐도 구별되는가? |
| 아이콘·카드 | 종류·가치·상태의 형태 언어; 핵심 의미와 장식의 우선순위 | 작은 슬롯과 긴 한국어에서 의미가 남는가? 색 없이도 종류/선택이 구분되는가? |
| 배경·공간 | 시선 유도·분위기·상호작용 대상과 장식의 구별 | HUD·이동 경로·중요 대상이 묻히지 않는가? 탐색 의도를 과도한 강조로 없애지 않는가? |
| 초상·서사 이미지 | 승인된 인물 정체성·표정·관계·감정 전환 | 예쁜 단독 그림이 아니라 대사·프레이밍과 맞고 정체성이 유지되는가? |
| 보상·수집·꾸미기 | 소유/변화/완성감과 취향의 표현 | 선택 전후 차이가 보이고 내 선택의 결과라고 느끼는가? |

자산별 실제 표시/원본 크기, 배경/투명 영역, crop-safe 영역, pivot, 필요한 변형·상태, 텍스트를 별도 렌더할지, 압축·필터링을 프로젝트 consumer에 맞춰 기록한다. 이미지에 번역할 UI 문자를 굽는 것이 기본안은 아니다. 규칙 없는 변형 대량 제작은 하지 않되 필요한 상태군을 빠뜨리지 않는다.

이미지가 실제로 필요하면 승인 자산·후보를 먼저 재사용한다. 새 이미지 제작·편집은 **이미지 모델**을 사용하고 직접 그린 SVG·Canvas·Python 그림으로 대체하지 않는다. 흐름·상태 표는 text-native로 유지한다. `GENERATED_CANDIDATE → REVIEWED → USER_APPROVED → CANON_REGISTERED → IMPLEMENTED → RUNTIME_VERIFIED`는 각각 별개다. 승격 시 provenance·SHA-256·저장소 경로·consumer·상태군을 기존 Asset Catalog/manifest에 연결한다. 이 가이드의 예시를 자산 승인으로 해석하지 않는다.

## 5. UI: 상태표는 겉모양이 아니라 동작 계약이다

상태는 모두 배타적인 하나의 enum이 아니다. **focused + selected**처럼 함께 존재할 수 있으므로 상호작용/선택/가용성/처리 결과의 축과 표시 우선순위를 정한다. 필요한 상태만 만들고 없는 기능의 loading/error 화면을 의무적으로 추가하지 않는다.

| 상태 | 사용자에게 전달할 것 | 입력·전환·복구 규칙 |
|---|---|---|
| normal / hover / focused | 무엇에 작용할 수 있고 현재 입력 대상은 무엇인지 | hover 정보는 지원하는 키보드·패드 포커스나 터치의 동등 경로에서도 제공 |
| pressed / selected | 눌림 접수와 유지되는 선택은 다름 | 선택했다고 실행/구매한 것은 아님; 취소와 재선택 뒤 표시 일치 |
| disabled | 지금 사용할 수 없는 이유와 복구 조건 | 회색만 남기지 않음; 비활성 버튼이 포커스를 못 받으면 인접 설명 등 도달 가능한 경로 제공 |
| locked | 아직 충족하지 못한 공개 가능한 해금 조건 | 미래 보상·서사 스포일러를 함부로 공개하지 않음 |
| loading | 실제 처리 중, 허용 입력·취소·시간 초과 후 복구 | 중복 요청·뒤 화면 입력 누수 방지; 영구 입력 잠금 방지 |
| success / error | 확정된 결과 또는 실패 이유·다음 행동 | 실패를 성공음으로 표현하지 않음; 재시도·닫기·초점 복귀를 정의 |

modal 닫기, 대상 삭제, 목록 재정렬, 입력 장치 변경, save/load 후 필요한 선택·포커스·스크롤 복원을 검토한다. 전체 화면·최소 폭·긴 한국어·텍스트 확대·밝고 어두운 배경·지원 입력에서 검사한다. 순수 미리보기·필터·정렬은 도메인 저장 변경과 구분한다. 데이터가 없을 때의 empty와 실패한 error도 혼동하지 않는다.

**사용성 개선은 정답 대행이 아니다.** 선택의 비용·결과를 이해하게 하되 승인되지 않은 추천 최적해, 자동 선택, 숨겨진 확률·단서 공개로 고민을 없애지 않는다. 정보 공개 시점과 정도도 프로젝트 경험의 일부다.

## 6. Godot 구현·성능·동등 경로

[Godot UI 계약](godot-ui-implementation-contract.md), [모션 계약](ui-motion-and-interaction-principles.md), [폴리싱 계약](ui-polishing-method.md)의 기존 구조와 프로젝트 채택 엔진 버전을 사용한다. 아래는 배치 방향이며 새 framework를 설치하라는 지시가 아니다.

| 책임 | 기존 Godot consumer에 연결할 내용 |
|---|---|
| 규칙 | 실제 state_owner·데이터/Resource·이벤트; UI는 표시 데이터와 Signal 의도만 교환 |
| UI | 재사용 Control/Container/Theme·컴포넌트 Scene, focus neighbor·초기/복귀 focus, 입력 전파 |
| 모션/VFX | 기존 AnimationPlayer/Tween/효과 Scene의 역할, 대상 node의 수명, 중단/재생/정리 |
| 오디오·설정 | 실제 bus·mute·개별 피드백 설정, 반복 제한과 설정 save/load가 필요한 경우의 owner |
| 자산 | 승인 Texture·Sprite/Material·아이콘·음원, 실제 슬롯, 없거나 늦게 로드될 때의 처리 |

Tween 중단은 자동으로 올바른 최종 표시를 보장한다고 가정하지 않는다. 중단 뒤 semantic state·표시·focus를 명시적으로 맞춘다. 같은 property를 여러 Tween이 동시에 덮는 충돌을 피한다. 도메인에서 승인된 전투 타이밍과 순수 장식 타이밍을 구분하고 장식 완료 callback에 구매·보상 처리를 맡기지 않는다.

`reduced motion / mute / haptic-off` 및 낮은 효과 설정에서도 필수 정보와 게임 판정은 유지한다. 색+형태는 색각 구별을 돕지만 모든 비시각 접근을 보장하지 않는다. 프로젝트의 접근성 범위에 필요한 음성·공간음·내레이션 등 다른 감각 경로를 별도 판단한다. 대체 신호를 정의하지 않은 필수 cue 누락은 조용히 통과시키지 않는다. 불필요한 움직임·깜박임은 축소/해제 경로를 설계하고 실제 검증 전 접근성 전체 PASS를 주장하지 않는다.

성능은 목표 기기·렌더러·해상도와 **동시 효과가 몰리는 대표 상황**의 측정 질문으로 정의한다. 기존 profiler로 frame time·메모리·draw call 등 필요한 지표만 본다. shader·particle·음원 수 상한, preload/pooling은 측정된 병목과 기존 해법이 있을 때 선택한다. UI 정립만을 이유로 분석 서버·상주 에이전트·유료 도구를 만들지 않는다.

## 8. 검증·교정·프로젝트 채택

기준 빌드와 후보 빌드 각각의 exact SHA, 같은 시나리오/seed·입력·해상도·설정·언어, 바뀐 변수를 기록한다. 가능한 작은 대표 구간에서 첫 노출과 반복 사용, 정상과 실패·중단·혼잡 조건을 비교한다. 대체 설정 검사는 핵심 표현을 전부 뺀 기술 PoC를 사람 경험 증거로 승격하는 수단이 아니다.

`DOC / MACHINE / RUNTIME / HUMAN / USER_APPROVAL / RELEASE`를 분리한다. 문서의 빈칸·링크·회귀 테스트 PASS는 실제 화면·감정·에이전트 준수 증거가 아니다. 관찰 행동·자기보고·필요 로그와 `counterevidence`를 대조한다. 구현 전에는 구현/사람 결과를 `NOT_RUN`으로 두며 `FUN_PASS`를 자동 생성하지 않는다.

- 못 봄 → 시선·대비·가림·동시 신호를 확인한다.
- 봤지만 오해함 → 의미·상태 구별·원인·문구를 확인한다.
- 이해했지만 재미없거나 피로함 → 감각·빈도·리듬·선택 구조를 검토한다. 단순히 더 큰 효과를 처방하지 않는다.
- 설정/재입력/복귀 시 깨짐 → 상태 소유·중단·이벤트·자산 수명을 고친다.

결과는 기존 Decision의 유지·변경·보류·재검증으로 연결한다. [프로젝트 어댑터](project-adapter-contract.md)에 따라 기존 UX/아트/시스템 원본·실제 consumer·검증 위치를 연결하고 선택 채택한다. **Base 문서·PR만으로 프로젝트 적용 완료가 아니며 `PENDING_PROJECT_ADOPTION`**이다. adopted lock을 일괄 바꾸거나 기존 승인 이미지를 교체하지 않는다.
