## Verified Base repair

The following changes are correctness and supply-chain hardening, not a
project-design choice:

1. allow the already-used `base_release.finalization_commit` field explicitly
   while retaining the strict closed-object Schema;
2. validate supplied finalization identity against Base's canonical release
   index and ancestry rather than accepting any 40-character SHA;
3. pin project validation to the trusted merged Base validator commit and verify
   the pinned commit contains the required contract implementation;
4. include fleet-hardening and rollout-status regressions in required Base CI;
5. keep released lock files immutable;
6. keep each project rollout isolated with exact-base and evidence gates.

## Approved decision A — protected baseline policy

### Selected: Option A — exact trusted-base equality

Require `protected_baseline.commit` to equal the trusted pull-request base or
remote-tracking base exactly. Baseline refresh and hash recomputation must occur
inside each project migration PR.

- Advantages: simplest authority model, strongest fail-closed behavior, easiest
  audit and incident reconstruction.
- Costs: every accepted project change advances the baseline and requires an
  automated refresh step.
- Decision: **APPROVED**.

### Rejected: Option B — ancestor baseline with protected-path proof

Permit an older ancestor baseline only when a separate trusted diff proves that
protected policy and protected paths were unchanged.

- Advantages: fewer baseline-only updates.
- Costs: more code, more evidence states, more room for authority mistakes, and
  harder review.
- Decision: **REJECTED_FOR_COMPLEXITY_AND_AUTHORITY_RISK**.

## Approved decision B — GRIMOIRE adapter authority

### Selected: Option A — restore the Base v1 thin adapter

Use `skills/PROJECT_BASE_ADAPTER.json` only for Base bindings, and move
GRIMOIRE-specific operating payload to a project-owned state artifact. Preserve
a compatibility view only for proven active consumers.

- Advantages: one shared adapter contract across projects, lower drift, and
  clearer project/Base ownership.
- Costs: requires a mapped migration and consumer audit.
- Decision: **APPROVED**.
- Rollout disposition in this record: **SEPARATELY_MANAGED**.

### Rejected: Option B — standardize a new Base-supported adapter v2

Promote GRIMOIRE's broader payload model into a new shared Base contract.

- Advantages: fewer immediate GRIMOIRE file moves.
- Costs: expands Base ownership into project planning and evidence state,
  duplicates existing project-health responsibilities, and increases migration
  cost for every other project.
- Decision: **REJECTED_FOR_OWNERSHIP_EXPANSION_AND_FLEET_COST**.
