# 게임 UX/UI 공용 체계 설계

## 1. 목적

여러 Godot 게임 프로젝트가 UX/UI 작업을 시작할 때 외형이나 컴포넌트부터 만들지 않고, 플레이어 경험·정보 구조·상호작용·상태·접근성·검증을 같은 순서와 증거 기준으로 설계하도록 공용 체계를 확장한다.

이 설계는 `auditing-and-refining-ui-art`의 기존 ID와 경로를 유지한다. 기존 스킬이 담당하던 구현 결과의 UI 아트 감사는 보존하고, 생성 전 UX 설계 계약을 별도 Skill Mode로 추가한다. 프로젝트는 공용 본문을 복제하지 않고 프로젝트 전용 책임 원본과 어댑터에서 차이만 기록한다.

## 2. 플레이어 약속

UX/UI 작업 결과는 플레이어가 다음을 스스로 설명하고 실행할 수 있게 해야 한다.

1. 지금 무엇이 중요한가.
2. 무엇을 할 수 있고 할 수 없는가.
3. 행동에 어떤 비용·위험·결과가 예상되는가.
4. 입력이 접수됐고 어떤 결과가 발생했는가.
5. 실패·잠금·오류의 원인과 복구 방법은 무엇인가.
6. 다음 행동이나 목표는 무엇인가.
7. 색·소리·모션 하나를 사용할 수 없어도 같은 의미를 얻을 수 있는가.

## 3. 범위

### 포함

- 핵심 플레이어 경험과 화면별 중심 질문
- 사용자 여정·화면 흐름·진입/이탈/복귀
- 정보 계층과 점진적 공개
- 입력·포커스·취소·되돌리기·파괴적 행동
- 컴포넌트 상태와 피드백 채널
- 디자인 토큰과 Godot Theme/Control/Container/재사용 Scene 계약
- 키보드·마우스·게임패드·터치 중 프로젝트가 선언한 입력 경로
- 접근성 장벽과 대체 경로
- 긴 한국어, 최소·목표 해상도, 안전 영역
- UX 가설·플레이테스트·인간 검증 상태
- 구현된 화면의 정적·런타임 UI 감사와 승인된 개선
- 레퍼런스의 `ADOPT / ADAPT / AVOID / TEST / IGNORE` 판정

### 제외

- 전투·경제·저장·진행 등 도메인 계산
- 플레이어가 보지 않는 내부 상태의 소유권 변경
- 최종 이미지·폰트·음향 자산 제작
- 프로젝트 코어와 중요 기획의 무단 변경
- 사람 플레이나 보조기기 검증을 자동 검사로 대체
- 특정 상용 디자인 시스템의 시각 양식 복제
- HTML 기획 대시보드 구축

## 4. 기존 스킬과의 경계

| 책임 | 담당 |
|---|---|
| 게임 코어·뾰족한 재미·경쟁작·플레이어 반응 | `analyzing-and-refining-game-concepts` |
| 기획 책임 원본 작성·발행 | `managing-design-documents` |
| UX/UI 설계 계약·Godot UI 계약·구현 화면 전문 감사 | `auditing-and-refining-ui-art` |
| 실패 가정 공격·비판 검증·최소 개선·회귀 | `running-adversarial-review-and-refinement` |
| diff·정적·런타임·접근성·성능 통합 증거 | `reviewing-and-validating-project-changes` |
| Vertical Slice의 대표 플레이·파이프라인·사람 증거 | `designing-vertical-slices` |
| 프로젝트 Skill 생성·통합·학습 | `evolving-project-discipline-skills` |

새 UX/UI 체계는 위 스킬의 권한을 재판정하지 않는다. 한 작업에서 주 분야 스킬은 하나만 선택하고 필요한 Foundation·검증 스킬만 지원 호출한다.

## 5. Skill Mode

### 5.1 `experience-contract`

화면이나 기능이 만들 플레이어 감정·판단·행동·보상과 성공 기준을 정의한다. 기능 목록이 아니라 플레이어가 인식하고 선택하고 확인하는 흐름을 출력한다.

### 5.2 `flow-and-information-architecture`

사용자 여정, 화면별 중심 질문, 첫 시선, 상시 정보, 선택 상세, 결과·복기, 진입·취소·복귀를 구조화한다. 한 화면이 여러 중심 질문을 동시에 떠맡으면 분리하거나 점진 공개한다.

### 5.3 `pattern-selection`

반복 UX 문제를 패턴 카드와 대조한다. 후보를 그대로 복사하지 않고 프로젝트 코어·플랫폼·입력·세션 길이에 맞춰 `ADOPT / ADAPT / AVOID / TEST / IGNORE`로 판정한다.

### 5.4 `design-system-contract`

토큰, 컴포넌트, 상태, 피드백 채널, 콘텐츠 문구, 예외·빈 상태·오류·파괴적 행동과 재사용 경계를 정의한다. 숫자는 공식처럼 고정하지 않고 목표 플랫폼과 사람 검증이 필요한 초기값으로 표시한다.

### 5.5 `godot-ui-contract`

기존 프로젝트 구조를 먼저 조사하고 `Theme`, `Control`, `Container`, 재사용 Scene, Signal, 포커스 이웃, 입력 액션과 상태 소유 경계를 정한다. 새 UI 프레임워크나 두 번째 상태 저장 계층을 기본으로 만들지 않는다.

### 5.6 `accessibility-gate`

정보·입력·탐색·시간·모션·음향·텍스트·인지 장벽을 찾고 동등한 경로를 설계한다. 기술 노출과 실제 사용자 접근성을 구분한다.

### 5.7 `playtest-contract`

정확한 build·commit·해상도·입력 장치·참가자·과제·가설·관찰 행동·설명 증거·중단 조건·통과 기준을 고정한다. 자동 테스트는 인간 이해 증거가 아니다.

### 5.8 `runtime-ui-audit`

기존 A~E 감사와 정적 후보 스캐너를 보존한다. 실제 실행 화면, 승인 방향, 파일·행·관찰 증거를 대조하고 자동 결함 확정이나 자동 수정을 하지 않는다.

### 5.9 `refine-approved-findings`

사용자가 승인한 UI finding만 구조 → 계층 → 타이포그래피 → 상태 → 장식 순으로 최소 수정한다. 도메인 규칙과 프로젝트 코어를 바꾸지 않는다.

### 5.10 `reaudit`

기존 판단을 보지 않은 새 검사 컨텍스트에서 전후 렌더·입력·해상도·폴백·회귀를 다시 검수한다.

## 6. 공용 산출물

### 6.1 프로젝트 UX/UI 책임 원본

프로젝트는 다음 항목을 하나의 현행 Markdown 원본에 둔다. 기존 UI 책임 원본이 있으면 새 파일을 만들지 않고 그 문서를 갱신한다.

- 플레이어 경험과 핵심 UX 약속
- 플랫폼·화면·입력 범위
- 사용자 여정과 화면별 중심 질문
- 정보 계층과 점진 공개
- 핵심 상호작용 패턴
- 컴포넌트·상태·피드백 계약
- 접근성 장벽·폴백
- Godot 상태 소유·Signal·Theme·Container 계약
- 검증 매트릭스와 `NOT_RUN / UNVERIFIED`
- 프로젝트 고유 패턴과 Base 환류 후보

### 6.2 패턴 카드

각 패턴은 다음을 포함한다.

```yaml
pattern_id:
problem:
player_risk:
use_when:
do_not_use_when:
core_flow:
required_states:
feedback_channels:
accessibility_fallbacks:
platform_adaptation:
failure_modes:
validation_predicates:
reference_evidence:
adoption_decision: ADOPT | ADAPT | AVOID | TEST | IGNORE
```

### 6.3 레퍼런스 카드

각 외부 참고는 출처·최종 확인일·적용 범위·변환 축·저작권/브랜드 복제 금지·채택 판정을 기록한다. 외부 자료는 요구사항이나 구현 사실의 정본이 아니다.

## 7. 공용 패턴 최소 세트

1. 시스템 상태 가시성
2. 입력 접수와 즉각 피드백
3. 예상 비용·위험·결과 미리보기
4. 점진적 공개와 필요 시점 학습
5. 비교 가능한 선택지
6. 취소·되돌리기·안전한 파괴적 행동
7. 오류 원인과 복구 경로
8. 포커스·탐색·입력 동등성
9. 색·소리·모션 외 동등 신호
10. 장기 복귀·재열람·기억 보조
11. 결과 인과·로그·복기
12. 빈 상태·잠금·로딩·중단·오프라인/누락 자산 폴백

## 8. Godot 구현 원칙

- 기존 Theme·레이아웃·편집기·상태 구조를 먼저 조사한다.
- UI는 표시 데이터를 입력받고 사용자 의도를 Signal로 반환한다.
- 도메인 규칙, 피해, 보상, 저장 결과를 UI 콜백에서 재계산하지 않는다.
- 반복 단위만 재사용 Scene으로 분리한다.
- `Container`가 레이아웃을 소유하고 수동 좌표는 의도와 검증 조건이 있을 때만 사용한다.
- 컴포넌트 상태는 최소 `normal / hover / focused / pressed / selected / disabled / locked / loading / error / new` 중 필요한 상태를 선언한다.
- 비활성·잠금은 이유와 해제 조건을 제공한다.
- 팝업이 닫히면 이전 의미 있는 포커스로 복귀한다.
- 최소·목표 해상도와 긴 한국어에서 잘림·겹침·포커스 순서를 검증한다.
- 접근성 설정과 폴백은 규칙 결과를 바꾸지 않는다.

## 9. 공식 레퍼런스 기준

공용 참고자료는 다음 종류를 우선한다.

- Xbox Accessibility Guidelines: 게임 UI·입력·포커스·목표·다중 채널·모션
- W3C WCAG 2.2: 인지 가능·운용 가능·이해 가능·견고성의 웹 기반 원칙 중 게임 UI에 적용 가능한 부분
- Godot 공식 문서: GUI navigation, Theme, Control, Container
- Apple Human Interface Guidelines: 게임·접근성·입력의 플랫폼 관점
- Material Design 3: 상호작용 상태와 토큰 구조를 Godot에 맞게 변환
- Nielsen Norman Group: 시스템 상태·현실 일치·사용자 통제·일관성·오류 예방·회상보다 인식·복구·도움말 등의 휴리스틱

브랜드 외형이나 수치 토큰을 그대로 복제하지 않는다. 공식 지침도 프로젝트 코어와 실제 플레이 증거에 맞춰 채택·변환·시험한다.

## 10. 검증

### 자동·정적

- Skill·reference·template 파일 존재
- Skill Mode·경계·출력 계약 존재
- 레퍼런스 URL·확인일·채택 판정 존재
- 프로젝트 어댑터가 Base Skill ID와 공용 원본을 연결
- 기존 UI 감사 스캐너 회귀 통과
- JSON·Markdown 참조 경로 최신성

### 런타임

- 선언된 해상도·입력 장치
- 포커스 시작·이동·복귀
- 정상·잠금·비활성·오류·빈 상태
- 긴 한국어·자산 누락·모션 감소·음향 끄기
- 시스템 상태와 결과 인과

### 인간

- 플레이어가 화면의 중심 질문과 다음 행동을 설명
- 선택 비용·위험·결과를 선택 전에 설명
- 실패 원인과 복구를 도움 없이 수행
- 색·소리·모션 폴백에서도 같은 의미를 이해

실행하지 않은 검증은 `NOT_RUN` 또는 `UNVERIFIED`로 유지한다.

## 11. 프로젝트 적용 전략

- `Blacksmith`: Android 세로형·터치·안전 영역·강화 위험과 보상 비교 중심.
- `GRIMOIRE-`: 마법 글자 직접 작성·인식 실패와 주문 설계 실패의 분리·점진 학습 중심.
- `omenward`: 위협 예고→릴 설계→배치→전투 결과의 인과와 3라인 우선순위 중심.
- `Ten-Paces-Hidden-Moves`: 적 의도 단서·3/3/4 계획·거리·합·중단·복기 중심.
- `urban-legend`: 조사 정보의 신뢰 상태·가설·규칙 검증·회수 결과·장기 기억 보조 중심.

프로젝트별 캐릭터·세계관·수치·실제 경로·검증 결과는 각 저장소에 남긴다.

## 12. 완료 기준

- 기존 Skill ID와 UI 감사 기능이 보존된다.
- UX 설계부터 런타임 감사까지 모드와 책임 경계가 명시된다.
- 공식 레퍼런스, 패턴 라이브러리, Godot 계약, 템플릿과 테스트가 한 단계 안에 발견된다.
- 다섯 대상 프로젝트가 공용 Skill을 복제하지 않고 프로젝트 전용 패턴과 책임 원본을 연결한다.
- 각 저장소의 main 병합 뒤 새 HEAD에서 정본·참조·PR·검증 상태를 재검토한다.
- 제품 코드·Scene·데이터·수치는 변경하지 않는다.
- 사람 플레이·실기기·보조기기·런타임을 실행하지 않은 경우 완료로 과장하지 않는다.
