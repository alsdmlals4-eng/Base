# Expression Studio ChatGPT Pro Same-Run Handoff Integration Design

## Status

Approved continuation of Issue #427 work order item 4 on provisional PR #428.

## Goal

Complete the no-additional-payment Character Studio golden path:

`reviewed request -> server-issued ChatGPT Pro handoff -> returned PNG import into the same run -> candidate review -> confirm/export -> exact Figma route receipt`

The normal production path remains `subscription_handoff_import` with `CHATGPT_INCLUDED`, `provider_call_made=false`, and `requires_additional_payment=false`.

## Existing contracts reused unchanged

- `ExpressionRequest` remains the canonical request model for expression/outfit/scene edits.
- Approved anchor route, project ownership, source SHA-256, and Figma node evidence remain mandatory.
- `generation_instruction(request, resolved)` remains the identity-preserving edit instruction source.
- `build_subscription_handoff_packet()` and `render_chatgpt_pro_prompt()` remain the only ChatGPT Pro prompt contract.
- Existing imported-image validation, duplicate/transparent/anchor-equality rejection, Asset Vault staging, lineage, candidate review, export, confirm-delivery, download, pairing, exact Figma routing, and receipt verification remain authoritative.
- Existing direct `/api/import-runs` remains available for compatibility and for non-ChatGPT included/local import workflows.

## Decision

### Server-issued pending handoff run

Expression Studio creates a pending handoff record before any image generation happens. The browser never invents or supplies a free-form run ID.

The pending record binds:

- `run_id` generated by the Studio server,
- exact validated `ExpressionRequest`,
- exact approved anchor SHA-256 and project-owned anchor evidence,
- resolved expression/edit instruction,
- expected candidate count,
- fixed declared source `CHATGPT_INCLUDED`,
- rendered ChatGPT Pro prompt,
- lifecycle state `GPT_PRO_HANDOFF_READY`.

The pending record is memory-only until returned PNGs are imported. No empty Asset Vault run directory is created at prompt-preparation time.

### Handoff preparation endpoint

Add a dedicated endpoint:

`POST /api/handoff-runs`

Request body: canonical `ExpressionRequest` JSON.

Response contains only public handoff data:

- `run_id`,
- `state=GPT_PRO_HANDOFF_READY`,
- `generation_surface=CHATGPT_PRO_SUBSCRIPTION`,
- `prompt`,
- display-only source filename and SHA-256,
- expected PNG count and dimension bounds,
- review checklist,
- `run_mode=subscription_handoff_import`,
- `declared_source=CHATGPT_INCLUDED`,
- `provider_call_made=false`,
- `requires_additional_payment=false`.

The response must not expose local absolute paths, Figma file keys/node routes, delivery credentials, API keys, Tool Hub tokens, or shell instructions.

### Same-run import endpoint

Add a dedicated endpoint:

`POST /api/handoff-runs/{run_id}/import`

The endpoint accepts only candidate files. Project/request/source truth comes from the pending server record, not from browser-supplied JSON.

Import rules:

1. `run_id` must identify one currently pending handoff.
2. Candidate count must equal the pending request count.
3. Every image is validated as `CHATGPT_INCLUDED` with existing bounded upload/image validation.
4. Before consuming the pending record, revalidate approved anchor ownership, route, SHA-256, and request evidence.
5. Existing `create_import_run` logic is reused with the reserved server-issued run ID.
6. On successful import, the pending record is consumed exactly once and the resulting generated run keeps that exact `run_id`.
7. Unknown, mismatched, already-consumed, or tampered handoffs fail closed.
8. A failed validation/import does not consume the pending record, allowing correction and retry with the same request/run identity.

## Service boundary

Refactor only enough to avoid duplicating import validation.

- Add `PendingHandoff` as a bounded internal record.
- Add `prepare_subscription_handoff(request)`.
- Extend the internal import implementation to accept an optional reserved run ID that is never exposed through the legacy direct-import API.
- Add `import_subscription_handoff(run_id, candidates)` that verifies and consumes a pending record and delegates to the shared import implementation.

No paid OpenAI provider adapter is called from this flow.

## UI flow

In `subscription_handoff_import` mode:

1. User fills project/anchor/edit controls.
2. User chooses `ChatGPT Pro 프롬프트 준비`.
3. Studio displays the copy-ready prompt and the server-issued run ID.
4. User generates the requested PNGs in their existing ChatGPT subscription surface.
5. User selects the returned PNG files in Studio and chooses `같은 Run으로 후보 가져오기`.
6. Existing candidate comparison UI appears.
7. User selects one candidate and uses existing `확정 및 전달`.
8. Existing project save, optional PC download, Figma pairing/status, and verified receipt flow continues unchanged.

The legacy direct import control remains available as a secondary path for Figma/local/other user-supplied assets. It must not be presented as the canonical ChatGPT Pro handoff path.

## Error handling

- Unsupported run mode: 409.
- Invalid request/anchor/route/evidence: 422 before a pending run is created.
- Unknown or consumed handoff: 404/409 without creating files.
- Wrong candidate count or invalid image: 422; pending run remains retryable.
- Anchor or registry changed after prompt preparation: 409/422; pending run remains unconsumed and no candidate run is created.
- Any provider call or additional-payment truth mismatch is a contract failure.

## Security and privacy

- Run IDs are server-generated opaque identifiers, not authorization credentials.
- CSRF/origin/session protections remain mandatory for both new POST endpoints.
- Handoff prompt contains no private routing material; existing renderer secret/private-path checks remain authoritative.
- Candidate upload stays bounded by the existing request-body and image validators.
- Asset Vault writes happen only after the pending handoff has been revalidated.
- Exact Figma routing and Hub delivery credentials remain outside the ChatGPT prompt and browser-created data.

## Testing contract

### RED/GREEN focused tests

- preparing a valid expression/outfit/scene handoff returns the fixed subscription/no-payment truth and a renderer-produced prompt.
- server generates the run ID; arbitrary browser run IDs are not accepted for preparation.
- exact pending `run_id` is preserved after candidate import.
- wrong/unknown/consumed run IDs fail closed.
- wrong candidate count, malformed image, duplicate image, anchor-equal image, or wrong project evidence leaves pending handoff retryable.
- anchor/registry mutation between prepare/import blocks import.
- successful import consumes once; replay cannot overwrite or create a second run.
- prompt has no Figma URL/key/node ID, absolute local path, token, provider/API key, or additional-payment claim.
- existing direct `/api/import-runs`, candidate review, confirm-delivery, download, pairing/status, and Figma exact-route tests remain green.

### Platform verification

Run focused tests and existing subscription/import/confirm/Figma suites on Ubuntu and Windows. Re-run the real Windows four-child multi-project smoke after integration.

## Scope exclusions

- No browser automation of ChatGPT.
- No clipboard automation requirement.
- No OpenAI API generation as the canonical path.
- No Figma destination entry by the user.
- No Sprite/Effect handoff UI expansion in this slice; their existing subscription import contracts remain unchanged.
- No changes to Local Executor #420 behavior.

## Rollback

The handoff feature is additive. Rollback removes the two new handoff endpoints/UI controls and pending-record service methods; legacy `/api/import-runs`, existing candidate review/export/delivery, Tool Hub/Figma integration, and Windows process ownership remain independently functional.
