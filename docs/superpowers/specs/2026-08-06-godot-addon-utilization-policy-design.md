# Godot 애드온 선택 활용 정책 설계

**상태:** APPROVED_DESIGN  
**승인:** 사용자 권장안 승인, 2026-08-06  
**대상:** `alsdmlals4-eng/Base` 공용 운영 규칙  
**범위:** Godot 프로젝트의 애드온 조사·채택·활용·제거 원칙

## 1. 목적

Base는 Godot 애드온을 무조건 많이 설치하거나 반대로 일괄 금지하지 않는다. 이미 검증된 애드온이 프로젝트의 현재 단계와 실제 문제를 해결한다면 직접 중복 구현보다 우선 활용하되, 프로젝트 코어·데이터 권위·세이브·출시 경계를 침범하지 않는 선택적 채택을 의무화한다.

이 정책의 핵심은 다음과 같다.

> 승인되고 검증된 애드온은 실제 필요가 발생한 프로젝트에서 적극 활용한다. 모든 프로젝트에 일괄 설치하지 않으며, 기능이 없는 단계에는 미리 넣지 않는다.

## 2. 배경과 현행 정본

Base에는 이미 다음 책임 원본이 있다.

- `AGENTS.md`의 Existing Solution First Gate
- `skills/evaluating-godot-assets-and-plugins-before-creation/SKILL.md`
- `docs/knowledge/godot/HIGODOT_SINGLE_AUTHORITY_AND_SAFE_OPERATION.md`

현행 규칙은 새 애드온을 만들기 전에 기존 대안을 조사하고 `REUSE / ABSORB / REFACTOR / ARCHIVE / BUILD_NEW`를 판정하도록 요구한다. 또한 HiGodot을 Godot 저작·편집 자동화의 단일 MCP/addon 실행 권위로 둔다.

그러나 “외부 애드온을 평가한다”는 규칙과 “평가를 통과한 애드온을 실제 프로젝트에서 활용한다”는 실행 원칙 사이가 충분히 명시적이지 않다. 이로 인해 다음 두 극단이 발생할 수 있다.

1. 이미 검증된 애드온이 있는데도 직접 구현한다.
2. 유용해 보이는 애드온을 모든 프로젝트에 미리 설치한다.

이번 변경은 이 간극만 닫는다. 새로운 독립 Skill이나 별도 애드온 Registry를 만들지 않는다.

## 3. 결정

### 3.1 공용 원칙만 Base에 둔다

Base에는 특정 프로젝트 이름과 애드온 배치표를 고정하지 않는다. 프로젝트별 현재 채택 상태는 각 프로젝트의 어댑터, 의존성 기록, `project.godot`, `addons/`, 테스트와 Decision이 책임진다.

Base는 다음 공용 판정 기준만 제공한다.

- 현재 단계에서 해결할 실제 문제가 있는가
- Godot 정확한 버전과 목표 플랫폼에서 동작하는가
- 프로젝트 코어와 데이터 권위를 침범하지 않는가
- 기존 구현과 권위가 중복되지 않는가
- 버전·출처·라이선스·제거 절차가 기록됐는가
- 별도 브랜치 또는 샘플에서 검증됐는가
- 채택 후 실제로 사용하는가

### 3.2 일괄 설치를 금지한다

다음은 금지한다.

- “언젠가 쓸 수 있다”는 이유로 모든 프로젝트에 복사
- 플러그인 수가 많을수록 개발 효율이 높다는 가정
- 같은 역할의 애드온을 둘 이상 활성 권위로 유지
- 프로젝트 단계가 기획뿐인데 테스트·대화·출시 플러그인을 미리 설치
- 설치만 하고 실제 코드·테스트·작업 흐름에서 사용하지 않음
- 제거·복구 방법 없이 핵심 Scene·세이브·데이터를 플러그인 형식에 결합

### 3.3 채택을 통과한 애드온은 적극 활용한다

평가 결과가 `REUSE` 또는 승인된 `REFACTOR`이고 현재 작업에 실제 효용이 있다면, 직접 중복 구현보다 애드온 활용을 우선한다.

채택 이후에는 다음 중 하나 이상의 소비 경로가 있어야 한다.

- 프로젝트 테스트 명령 또는 CI
- 편집기 작업 흐름
- 런타임 기능
- 플랫폼 빌드·서비스 연결
- 콘텐츠 제작 파이프라인

소비 경로가 없다면 `INSTALLED_UNUSED`로 판정하고 제거하거나 도입을 연기한다.

## 4. 애드온 유형별 기본 라우팅

이 절은 특정 제품에 대한 고정 설치표가 아니라 공용 단계 기준이다.

### 4.1 HiGodot / Godot AI

- 역할: Godot 편집·저작 자동화와 연결된 단일 MCP/addon 실행 권위
- 사용 시점: Godot 제품 프로젝트에서 AI 편집 자동화가 필요한 경우
- 금지: 같은 저작 권위를 가진 별도 MCP·라이브 에디터·자동화 플러그인을 병렬 활성화
- 허용: 테스트, 대화, 플랫폼 서비스처럼 역할이 다른 비저작 애드온

HiGodot 단일 권위는 다른 모든 애드온을 금지한다는 뜻이 아니다. 동일한 편집·저작 실행 권위의 중복만 금지한다.

### 4.2 테스트 프레임워크

- 사용 시점: 테스트 가능한 제품 코드나 상태 규칙 구현이 시작될 때
- 기본 판정: 반복 가능한 게임 규칙, 저장·불러오기, 경제·전투·퍼즐·분기 로직이 있으면 채택 우선 검토
- 보류 시점: 기획 전용 저장소, 실행 가능한 제품 코드가 없는 단계
- 요구: 실제 테스트 파일·명령·CI 소비 경로와 버전 고정

테스트 프레임워크는 폴더만 추가하는 장식이 아니다. 테스트를 작성하고 실행할 계획이 없으면 설치하지 않는다.

### 4.3 대화·서사 프레임워크

- 사용 시점: 분기, 조건, 화자, 현지화, 저장 복구, 콘텐츠 편집 요구가 자체 데이터 구조보다 복잡해질 때
- 선행 비교: 기존 JSON·Resource·Scene 기반 대화 시스템과의 책임 중복, 마이그레이션 비용, 저장 호환성
- 금지: 이미 운영 중인 사건·대화 정본을 평가 없이 교체
- 요구: 작은 대표 대화 흐름으로 시험하고 제거·변환 절차를 기록

### 4.4 플랫폼 서비스 애드온

대상 예시는 Google Play Billing, Google Play Games, Steam 연동이다.

- 사용 시점: 해당 플랫폼 기능이 승인된 출시 범위에 포함되고 실제 통합 작업을 시작할 때
- 보류 시점: 플랫폼이 미래 후보이거나 결제·업적·클라우드 저장 요구가 승인되지 않았을 때
- 요구: 목표 플랫폼별 빌드 분리, 자격 증명 비공개, 테스트 트랙, 실패 시 게임 코어의 독립 실행
- 금지: PC·Android·Steam 플러그인을 모든 프로젝트에 동시에 선설치

### 4.5 개발 편의·카메라·아이콘 애드온

- 사용 시점: 실제 반복 작업을 줄이거나 승인된 UX·카메라 요구를 명확히 충족할 때
- 기본 판정: Godot 기본 노드·리소스·편집 기능으로 충분하면 추가하지 않음
- 요구: 빌드 포함 여부, 런타임 의존성, 제거 후 Scene 복구 여부 확인

## 5. 채택 상태 모델

프로젝트별 애드온은 다음 상태 중 하나로 기록한다.

```text
CANDIDATE
TRIAL_APPROVED
ADOPTED_ACTIVE
ADOPTED_DISABLED
DEFERRED
REJECTED
INSTALLED_UNUSED
REMOVAL_PENDING
REMOVED
```

최소 기록 필드는 다음과 같다.

```yaml
addon_name:
role:
exact_version:
source:
license:
godot_compatibility:
platform_scope:
adoption_state:
consumption_path:
owner_boundary:
validation:
rollback_or_removal:
unverified:
```

Base는 이 데이터를 한 중앙 파일에 수집하지 않는다. 각 프로젝트의 기존 third-party inventory 또는 의존성 책임 원본에 기록한다.

## 6. 변경 위치

새 Skill을 만들지 않고 기존 책임 원본을 보강한다.

### 수정 대상

1. `AGENTS.md`
   - Existing Solution First Gate에 “검증·승인된 애드온은 실제 필요가 있을 때 중복 구현보다 활용을 우선하되 일괄 설치하지 않는다”는 불변 원칙을 짧게 추가한다.

2. `skills/evaluating-godot-assets-and-plugins-before-creation/SKILL.md`
   - `adoption-decision` 뒤에 선택적 활용·소비 경로·`INSTALLED_UNUSED` 판정을 추가한다.
   - 테스트, 대화, 플랫폼, 개발 편의 애드온의 단계별 라우팅을 추가한다.
   - 프로젝트별 이름과 고정 배치표는 넣지 않는다.

3. `docs/knowledge/godot/HIGODOT_SINGLE_AUTHORITY_AND_SAFE_OPERATION.md`
   - HiGodot 단일 권위의 범위를 저작·편집 자동화로 한정한다.
   - 역할이 다른 검증된 테스트·대화·플랫폼 애드온과 공존 가능함을 명시한다.
   - 동일 저작 권위의 병렬 활성화만 금지한다.

### 검증 대상

기존 계약 테스트의 소유 위치를 확인해 다음 불변 조건을 추가한다.

- 공용 정책이 특정 프로젝트 이름을 포함하지 않는다.
- `일괄 설치 금지`와 `승인된 애드온 활용 우선`이 함께 존재한다.
- HiGodot 단일 저작 권위가 비저작 애드온 전면 금지로 해석되지 않는다.
- `INSTALLED_UNUSED` 제거·연기 규칙이 존재한다.
- 신규 ACTIVE Skill 수가 증가하지 않는다.

## 7. 오류·충돌 처리

### 애드온이 Godot에서 인식되지 않을 때

- `addons/<name>/plugin.cfg` 구조
- UTF-8 인코딩
- `.gdignore`
- 중첩 `addons/addons`
- 정확한 Godot 버전
- Parse Error와 의존 파일

을 먼저 확인한다. 인식 실패를 이유로 즉시 다른 애드온을 중복 설치하지 않는다.

### 애드온이 제품 코드와 충돌할 때

1. 애드온 비활성화 가능 여부 확인
2. 격리 브랜치에서 재현
3. 데이터·Scene 변환 여부 확인
4. bounded patch 가능성 검토
5. `REFACTOR / ARCHIVE / BUILD_NEW` 재판정

핵심 데이터 손상이나 저장 호환성 불명이면 채택을 중단한다.

## 8. 검증 전략

### 정적 검증

- 관련 Markdown의 필수 문구와 상호 참조 검사
- Registry의 ACTIVE Skill 수 불변
- 구형·중복 애드온 정책 검색
- 특정 프로젝트 이름이 공용 정책에 들어가지 않았는지 검사
- `git diff --check`

### 행동 검증

정책 기반 예시 입력에서 다음 판정이 나와야 한다.

1. 구현 전 기획 프로젝트에 테스트 프레임워크 설치 요청 → `DEFERRED`
2. 반복 가능한 퍼즐 규칙 구현 프로젝트에서 테스트 프레임워크 검토 → `REUSE/TRIAL` 우선
3. HiGodot 사용 프로젝트에 별도 저작 MCP 추가 요청 → 중복 권위로 차단
4. HiGodot 사용 프로젝트에 GUT 추가 요청 → 역할 분리 후 허용 가능
5. 미래 Steam 후보라는 이유로 Steam 플러그인 선설치 → `DEFERRED`
6. 설치됐지만 소비 경로 없는 애드온 → `INSTALLED_UNUSED`

실제 Godot Runtime, Android 빌드, Steam·Google 서비스 연결은 이번 Base 정책 문서 변경의 검증 범위가 아니다.

## 9. 비목표

- 특정 프로젝트에 실제 애드온을 설치하거나 제거하지 않는다.
- 프로젝트별 권장 애드온 표를 Base에 고정하지 않는다.
- 애드온 파일을 Base 저장소에 직접 배포하지 않는다.
- HiGodot 버전을 변경하지 않는다.
- GUT, Dialogue Manager, Google Play, Steam 플러그인을 자동 승인하지 않는다.
- 외부 라이선스·가격·호환성의 현재 상태를 이 문서 하나로 영구 보증하지 않는다.

## 10. 완료 기준

- Base 공용 규칙에 애드온 선택 활용 원칙이 명시된다.
- 승인된 애드온 활용과 일괄 설치 금지가 동시에 적용된다.
- 프로젝트 단계별 도입 시점이 구분된다.
- HiGodot 단일 권위와 비저작 애드온 공존 경계가 명확하다.
- 프로젝트별 상태를 Base에 복제하지 않는다.
- 기존 Skill을 보강하며 ACTIVE Skill 수를 늘리지 않는다.
- 정적 계약과 관련 행동 검증이 통과한다.
- 프로젝트별 실제 설치는 별도 승인·검증 작업으로 남는다.
