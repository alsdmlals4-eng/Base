Current official Steam disclosure says generative AI assisted programming, music, and store-description drafting/editing; the current page says visual artwork and sound effects are procedurally generated by the game code, with no runtime AI or external AI service during play. Older cached/localized Steam surfaces can show a broader disclosure, so current direct official readback is required instead of treating cached wording as permanent truth.

Source: https://store.steampowered.com/app/4447940/Neon_Angora_The_Cabaret_Club/

```yaml
release_state: EARLY_ACCESS
ai_use_lane: RUNTIME_GENERATIVE

```

The developer describes fully local/offline Llama.cpp dialogue, CUDA/Vulkan backends, RAG memory, and real-time unscripted NPC conversation. Current Steam requirements expose a substantial local execution surface: minimum 16 GB RAM and an 8 GB VRAM-class GPU, with 32 GB RAM and 12 GB+ VRAM recommended. These requirements do not prove that the LLM alone causes the entire hardware budget; they do prove that a local runtime-AI design cannot be treated as zero-footprint merely because it avoids a provider/API bill.

Disposition: `TEST` only.

## 5. Material Base finding

### RUNTIME_AI_DEPLOYMENT_MODE_BUDGET

The 2026-08-24 Radar already requires latency/offline fallback, privacy/moderation/security, cost approval, platform/store compliance, and replay/debug evidence. The new comparison exposes one missing explicit branch: **local and remote runtime AI fail in different deployment budgets and must be audited separately before either is called cheaper, safer, offline-friendly, or production-ready.**

```text
runtime generative candidate
→ deployment_mode = LOCAL_MODEL | REMOTE_PROVIDER | HYBRID

LOCAL_MODEL
→ LOCAL_MODEL_RESOURCE_BUDGET
   model/quantization/backend
   download + installed footprint
   RAM / VRAM
   CPU / GPU support
   cold-start + response latency
   thermal/power/performance contention
   minimum/recommended device matrix
   unsupported-device fallback

REMOTE_PROVIDER
→ REMOTE_PROVIDER_TRANSPORT_BUDGET
   provider/model/version authority
   network requirement
   request/response latency
   outage / rate-limit / auth failure
   recurring cost
   privacy/data-transfer boundary
   moderation/safety surface
   provider migration/fallback

HYBRID
→ both budgets + consistency/failover ownership
```

```text
LOCAL_IS_NOT_FREE
REMOTE_IS_NOT_ZERO_FOOTPRINT
```

This does not promote runtime AI. `CAPABILITY_CONTRACT`, deterministic state validation, memory/canon boundary, replay/debug evidence, and project-owned authoritative GameState remain mandatory.

### Alternatives considered

1. `NO_CHANGE / rely on generic cost+platform gates` — rejected because local model resource pressure and remote transport/provider risk remain too easy to collapse into one vague budget.
2. `NEW RUNTIME AI MODULE/FRAMEWORK` — rejected as over-design; there are no shared code consumers or runtime proof.
3. `ADAPT EXISTING RADAR` — selected. It is the smallest existing-owner delta and stays research/process-only.
