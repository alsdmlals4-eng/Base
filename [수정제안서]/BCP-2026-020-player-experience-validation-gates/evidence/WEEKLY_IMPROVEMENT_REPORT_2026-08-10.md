# 2026-08-10 주간 작업 개선 보고서 — BCP-2026-020 근거 정리본

## 문서 목적

이 문서는 2026-08-10 주간 조사 보고서의 내용을 BCP-2026-020에 연결하기 위해 재정리한 근거 문서다.

원 보고서의 분류를 유지한다.

- A. 메인게임
- B. 미니게임
- C. 글쓰기
- D. 종합 반영안

단, 변동성이 큰 리뷰 수치·출시 상태·순위는 장기 Base 원칙의 근거로 사용하지 않는다. 외부 작품과 연구 사례는 **어떤 설계 질문을 검토했는가**를 보조하는 벤치마크로만 남기고, 실제 승격 판단은 Base 현행 owner와 프로젝트 계약을 우선한다.

---

# 0. 이번 주 핵심 결론

이번 주 최우선 개선점은 새 기능이나 새 Skill을 더 만드는 것이 아니라 다음 폐쇄 루프를 강화하는 것이다.

```text
AI 작업계약
→ 실제 구현 또는 플레이
→ 기술 증거
→ UI 증거
→ 사람 사용성 증거
→ 플레이어 경험 증거
→ 다음 작업 판단
```

공통 핵심 원칙은 다음과 같다.

> 설명과 시스템을 더하는 것보다 플레이어가 보고, 판단하고, 결과를 이해하고, 다음 선택을 바꾸는 주기를 더 명확하게 만든다.

이를 위해 BCP-2026-020은 다음 네 가지 후보를 추출한다.

1. `PLAYER_EXPERIENCE_EVIDENCE_GATE`
2. `FIRST_10_MINUTES_CONTRACT`
3. `DECISION_SCREEN_RULE`
4. `MINIGAME_NARRATIVE_FUNCTION_GATE`

`Context Budget`은 이번 보고서에서 중요성이 다시 확인됐지만 이미 BCP-2026-004가 owner이므로 신규 승격하지 않는다.

# A. 메인게임

## A-1. 이번 주 핵심 변화와 근거

여러 프로젝트의 기획·Vertical Slice·UI 계약이 구체화되면서, 단순 기능 완성보다 **플레이어가 실제로 무엇을 고민하고 있는가**를 검증할 필요가 커졌다.

특히 `urban-legend`의 메인 진입 화면을 단순 메뉴가 아니라 세계관 정체성·현재 상황·다음 행동이 함께 보이는 관제실형 경험으로 다루는 방향은 공용 원리로 일반화할 가치가 있다.

다만 공용 Base에는 특정 레이아웃이나 캐릭터를 올리지 않고 다음 원칙만 가져간다.

> 메인 화면은 세계관 정체성, 현재 상태, 다음 핵심 행동을 동시에 전달해야 한다.

## A-2. 현재 작업 방식의 개선점

현재 프로젝트들은 설계·구현·테스트·CI의 구분이 정교해졌다. 다음 단계는 **문서/기술 완료와 플레이어 경험 완료를 별도로 관리하는 것**이다.

권장 상태 구분:

| 상태 | 의미 |
|---|---|
| DESIGN PASS | 기획 논리가 성립 |
| IMPLEMENTATION PASS | 실제 동작 존재 |
| TECH QA PASS | 자동 테스트·파싱·회귀 검증 |
| UI PASS | 화면·입력·포커스·해상도 검증 |
| HUMAN USABILITY PASS | 처음 보는 사람이 조작과 다음 행동을 이해 |
| PLAYER EXPERIENCE PASS | 의도한 고민·감정·선택·보상이 실제로 발생 |

핵심은 `TECH QA PASS != PLAYER EXPERIENCE PASS`이다.

## A-3. 직접 경쟁작·인접 장르·장르 밖 벤치마킹

원 보고서에서는 다음 종류의 사례를 검토했다.

- `Foghorns Drown`: 강한 역할·장소·미스터리 정체성과 분위기만으로는 충분하지 않으며, 실제 플레이 판단이 필요하다는 경고 사례.
- `Demon Lord: Just a Block`: 설명을 줄이고 플레이어가 발견하게 하는 정보 절제 사례.
- `Moonlighter` 계열: 서로 다른 시스템이 존재하는 것보다 한 시스템의 결과가 다음 시스템의 결정을 바꾸는 연결 구조가 중요하다는 사례.

Base에 남길 벤치마킹 질문:

```text
이 시스템은 별도로 재미있는가?
보다
이 시스템의 결과가 다음 시스템의 결정을 바꾸는가?
```

## A-4. 핵심 플레이어 경험

각 게임은 장르명이 아니라 **플레이어가 반복해서 하게 되는 고민**을 한 문장으로 설명할 수 있어야 한다.

예시:

- `urban-legend`: 어떤 기록을 믿고 어떤 위험을 감수할 것인가.
- `Blacksmith`: 제한된 재료와 누적 위험 속에서 지금 멈출지 더 도전할지 결정한다.
- `omenward`: 현재 전장과 다음 위협을 보고 어떤 병력·자원을 배분할지 결정한다.
- `Ten-Paces-Hidden-Moves`: 제한된 행동·자원 안에서 어떤 무공 연계를 완성할지 고민한다.
- `ninja-survival-godot`: 전투 성장과 휴식/배낭 선택을 통해 다음 전투의 빌드를 바꾼다.
- `Switchy-Express-Cargo-Puzzle`: 제한된 선로·적재 규칙으로 배송 순서를 해결한다.

기능이 이 고민을 강화하지 못하면 우선순위를 낮춘다.

## A-5. 첫 10분 또는 첫 장면의 인상

권장 기본 흐름:

| 구간 | 목표 경험 |
|---|---|
| 초반 | 대표 문제를 눈앞에 보여준다 |
| 다음 | 문제를 다룰 대표 행동을 하나 준다 |
| 중반 | 의미 있는 첫 선택을 만든다 |
| 후반 | 선택의 결과와 이유를 보여준다 |
| 종료점 | 다음에는 무엇을 다르게 할지 질문이 생긴다 |

시간 자체는 강제값이 아니다. 장르에 따라 조정한다.

중요한 것은 첫 10분 안에 모든 시스템을 알려주는 것이 아니라 **대표 경험의 축소판을 한 번 완주시키는 것**이다.

## A-6. 핵심 루프 또는 장면 진행 구조

공용으로 추상화 가능한 루프:

```text
관찰
→ 선택
→ 비용 지불
→ 결과
→ 이유 이해
→ 새로운 선택
```

좋은 루프는 같은 행동의 반복보다 **판단 수정의 반복**이다.

## A-7. 반복 피로도와 감정 곡선

콘텐츠가 달라도 플레이어가 매번 같은 질문만 풀면 반복감이 생긴다.

예를 들어 조사 게임에서 매 사건이 `기록 읽기 → 정답 선택 → 미니게임 → 결과`로 동일하다면 사건 설정이 달라도 인지 과제가 반복된다.

반복 피로를 낮추기 위해 사건별 핵심 질문을 바꾼다.

- 무엇이 사실인가
- 누구를 믿는가
- 언제 위험을 감수하는가
- 무엇을 포기하는가
- 지금 철수해야 하는가
- 안전한 결과와 완벽한 결과 중 무엇을 택하는가

## A-8. 선택과 결과, 보상 또는 정보 공개 구조

주요 선택은 최소 두 층의 결과를 가져야 한다.

```text
선택
→ 즉시 보이는 변화
→ 이유 또는 원인 확인
→ 다음 선택 조건 변화
```

단순 수치 상승만으로 끝내지 않고, 플레이어가 `내가 저 선택을 해서 이것이 달라졌다`고 인식할 수 있어야 한다.

## A-9. 온보딩·UI/UX

핵심 화면은 모든 기능을 보여주는 메뉴판보다 **현재 결정을 돕는 화면**이어야 한다.

권장 질문:

```text
현재 상황은 무엇인가?
무엇을 선택할 수 있는가?
선택에 필요한 정보는 무엇인가?
선택하면 어떤 비용·위험·결과가 예상되는가?
```

이 네 질문은 BCP-2026-020의 `DECISION_SCREEN_RULE`로 추출한다.

## A-10. 비주얼 아이덴티티·마스코트·상징

1인 개발에서는 고비용 아트보다 **반복해서 기억되는 시각 언어**가 중요하다.

프로젝트별 후보 예:

| 프로젝트 | 대표 기억 장치 후보 |
|---|---|
| urban-legend | 괴이 기록 문서, 관제실, 아카 |
| Blacksmith | 대장간 불꽃, 완성 장비, 강화 흔적 |
| Ten-Paces-Hidden-Moves | 문파·무공 배지, 카드, 행동 자원 |
| omenward | 병영 편성, 전장 실루엣, 마력 흐름 |
| ninja-survival-godot | 닌자 유파, 배낭 빌드, 휴식 대비 전투 |
| Switchy-Express-Cargo-Puzzle | 열차·화물·분기 선로·배송 상태 |

구체 캐릭터와 자산은 프로젝트 전용으로 남긴다.

## A-11. 콘텐츠 제작 비용과 1인 제작 현실성

우선 투자할 구조:

```text
공통 프레임
+ 데이터 변형
+ 제한된 연출 차이
```

비용이 커지는 구조:

```text
에피소드마다 전용 Scene
+ 전용 UI
+ 전용 규칙
+ 전용 애니메이션
+ 전용 QA
```

기능 수가 아니라 **반복 제작 비용**을 함께 평가한다.

## A-12. 판매 포인트 또는 플레이어 유입 포인트

세일즈포인트는 기능 개수보다 한 장면으로 설명 가능한 핵심 고민에 가깝다.

권장 질문:

> 스크린샷 한 장 또는 짧은 GIF 하나로 플레이어가 이 게임에서 어떤 고민을 하는지 이해할 수 있는가?

## A-13. 성공 요인과 실패·이탈 요인

성공 요인:

- 선택의 의미가 읽힌다.
- 결과가 빠르게 보인다.
- 실패 이유를 이해할 수 있다.
- 다음 시도에서 바꿀 행동이 생긴다.
- UI와 세계관이 같은 경험을 강화한다.

이탈 요인:

- 시스템은 많은데 무엇이 중요한지 모르겠다.
- 결과는 나오지만 이유를 알 수 없다.
- 첫 구간에서 설명이 행동보다 앞선다.
- 부가 시스템이 코어 루프를 자주 끊는다.

## A-14. 그대로 참고할 요소

- 설명보다 빠른 대표 행동
- 짧은 첫 목표
- 결과와 원인의 연결
- 환경·UI를 이용한 세계관 전달
- 한 시스템의 결과가 다음 시스템의 판단에 영향을 주는 구조

## A-15. 현재 프로젝트에 맞게 변형할 요소

- 관제실/허브는 각 프로젝트의 세계관에 맞는 `결정 허브`로 변형.
- 첫 10분은 게임별 세션 길이에 맞춰 시간보다 대표 경험 완료를 우선.
- 결과 화면은 프로젝트마다 `복기`, `기록`, `작품 평가`, `다음 편성`, `다음 빌드` 등 다른 역할로 변형.

## A-16. 도입하지 말아야 할 요소

- 모든 시스템을 처음부터 노출
- 벤치마크 작품의 표면 UI를 그대로 복제
- 분위기와 설정으로 핵심 플레이 부족을 감추기
- 사람 검증 없이 자동 테스트를 제품 완성도로 표현
- 1인 제작에서 재사용 불가능한 전용 시스템을 계속 추가

## A-17. 작은 실험과 성공 기준

### 실험 A1 — 첫 10분 무설명 테스트

테스터에게 별도 설명 없이 대표 Vertical Slice를 플레이하게 한다.

성공 기준:

- 대표 문제를 설명할 수 있다.
- 핵심 행동을 스스로 찾는다.
- 첫 선택 이유를 설명할 수 있다.
- 결과가 왜 달라졌는지 설명할 수 있다.
- 다음에는 무엇을 바꾸고 싶은지 말할 수 있다.

### 실험 A2 — 결정 화면 감사

대표 화면 하나에서 기능명·버튼명을 가리고도 플레이어가 `지금 무엇을 결정해야 하는 화면인지` 설명 가능한지 확인한다.

성공 기준:

- 핵심 결정 1개가 명확하다.
- 보조 정보와 핵심 정보의 계층이 구분된다.

# B. 미니게임

## B-1. 이번 주 핵심 변화와 근거

미니게임은 본편을 잠시 쉬는 별도 놀이가 아니라 **본편에서 배운 정보를 짧은 행동으로 시험하는 장치**로 보는 것이 현재 프로젝트 구조에 더 적합하다.

원 보고서에서는 복잡한 정보를 증거 탐색·보고서 완성으로 바꾸는 연구형 게임 사례를 참고해, 미니게임의 역할을 `정보 → 판단 → 행동 → 결과`로 재정의했다.

## B-2. 현재 작업 방식의 개선점

미니게임마다 구현 전에 세 질문을 통과시킨다.

1. 본편에서 얻은 정보를 실제로 사용하는가?
2. 본편의 감정·서사·시스템 결과를 강화하는가?
3. 실패가 학습이나 상태 변화를 남기는가?

세 질문에 모두 약하면 별도 미니게임 구현 우선순위를 낮춘다.

## B-3. 직접 경쟁작·인접 장르·장르 밖 벤치마킹

원 보고서에서 검토한 사례:

- `Privacy Detective`: 복잡한 문서·근거를 플레이어 판단 과제로 변환하는 사례.
- `Pony Island 2`: 장르 전환과 다양한 놀이 자체가 정체성인 경우의 참고점이자, 무분별한 미니게임 확대의 경고 사례.
- AI-native game 관련 연구: 생성 방식보다 목표·규칙·상태·피드백·선택이라는 게임 기계 구조가 우선이라는 참고점.

Base에 남길 질문:

> 이 미니게임은 새 조작을 제공하는가가 아니라, 본편의 어떤 판단을 더 잘 느끼게 만드는가?

## B-4. 핵심 플레이어 경험

공통 정의:

> 본편에서 배운 정보를 짧은 행동으로 시험하고, 그 판단의 결과를 확인한다.

## B-5. 첫 30초 또는 첫 규칙 인상

처음 알려줄 것은 세 가지면 충분하다.

```text
무엇을 해야 하는가
어떤 정보를 사용해야 하는가
틀리면 무엇이 달라지는가
```

세부 조작과 예외 규칙은 실제 행동 시점에 단계적으로 노출한다.

## B-6. 핵심 루프

```text
정보 확인
→ 판단
→ 행동
→ 즉시 피드백
→ 정보 또는 가설 수정
```

## B-7. 반복 피로도와 감정 곡선

미니게임 개수보다 **인지 과제의 종류**를 관리한다.

재사용 가능한 공통 인지 프레임:

| 프레임 | 질문 |
|---|---|
| 판별 | 무엇이 잘못됐는가 |
| 순서 | 어떤 순서가 맞는가 |
| 연결 | 어떤 근거가 어떤 결론을 지지하는가 |
| 배치 | 제한된 공간·자원에 무엇을 어디에 놓는가 |
| 위험 선택 | 어느 정도 위험을 감수할 것인가 |

프로젝트마다 같은 프레임에 다른 데이터와 연출을 얹는다.

## B-8. 선택과 결과, 보상 또는 정보 공개 구조

실패도 플레이여야 한다.

실패가 남길 수 있는 것:

- 잘못된 가설 제거
- 새로운 위험 사례
- 추가 단서
- 인물 반응
- 자원 손실 또는 상태 변화
- 다음 시도 힌트

단순 `실패 → 즉시 재시작`만 반복되는 경우 본편과의 연결성이 약하다.

## B-9. 온보딩·UI/UX

미니게임 핵심 화면에는 최소한 다음이 읽혀야 한다.

```text
현재 질문
관련 정보
현재 선택
결과 또는 위험
```

화려한 애니메이션은 그 다음이다.

## B-10. 비주얼 아이덴티티·상징

독립 미술 스타일을 새로 만들기보다 프로젝트의 기존 시각 언어를 재사용한다.

예:

- `urban-legend`: 보고서, 검열선, 위험 도장, 조사 기록
- `Ten-Paces-Hidden-Moves`: 카드, 사거리, 행동 슬롯, 기력/내력
- `Blacksmith`: 재료, 열, 타격, 완성도
- `omenward`: 병력 역할, 전술 지도, 마력 흐름

이 방식은 제작비와 브랜드 일관성을 동시에 개선한다.

## B-11. 콘텐츠 제작 비용과 1인 제작 현실성

구현 비용보다 지속 콘텐츠 비용을 본다.

```text
1회 구현 비용
+ 에피소드별 데이터 비용
+ 아트 비용
+ 튜토리얼 비용
+ 실패/예외 QA 비용
+ 모바일/PC 입력 대응 비용
```

다음 콘텐츠에서 재사용할 수 없는 미니게임은 매우 비싼 시스템으로 분류한다.

## B-12. 판매 포인트 또는 유입 포인트

`여러 종류의 미니게임` 자체보다 다음과 같은 문장이 더 강한 판매 포인트가 될 가능성이 높다.

> 조사한 규칙을 실제 현장에서 검증한다.

즉 미니게임의 수가 아니라 **본편 정보가 행동으로 바뀌는 경험**을 판다.

## B-13. 성공 요인과 실패·이탈 요인

성공 요인:

- 본편에서 얻은 정보를 실제로 사용
- 규칙 설명이 짧음
- 성공/실패 이유가 명확함
- 실패가 다음 판단에 정보 제공
- 공통 프레임으로 재사용 가능

이탈 요인:

- 새로운 조작을 계속 학습해야 함
- 본편과 분위기·규칙이 단절됨
- 실패가 시간만 소모함
- 미니게임마다 별도 UI·자산·코드가 필요함

## B-14. 그대로 참고할 요소

- 근거 연결형 문제
- 정보 판별형 문제
- 실패에서 정보 획득
- 짧은 규칙 학습
- 본편 데이터 재사용

## B-15. 현재 프로젝트에 맞게 변형할 요소

- 도시괴담: `기록 → 모순 → 규칙 후보 → 현장 검증 → 기록 수정`
- 대장장이: 별도 리듬게임보다 강화 판단과 위험 선택을 보조하는 짧은 조작
- 전술: 코어 전투를 미니게임으로 축소하지 않고 부가 이벤트만 Gate 적용
- 퍼즐: 퍼즐 자체가 메인게임이면 `MINIGAME`이 아니라 `CORE_INTERACTION`으로 취급

## B-16. 도입하지 말아야 할 요소

- 본편 정보 없이도 풀 수 있는 장식성 미니게임
- 룰렛·클릭·반사신경을 이유 없이 삽입
- 메인 코어를 `미니게임`으로 오분류
- 실패 의미 없이 재시작만 반복
- 재사용 계획 없는 에피소드 전용 시스템 남발

## B-17. 작은 실험과 성공 기준

같은 게임 규칙 하나를 세 형식으로 기획한다.

1. 일반 선택지
2. 짧은 판별 인터랙션
3. 근거 연결 미니게임

성공 기준:

- 설명 30초 안에 이해 가능
- 짧은 플레이 안에 판단과 결과가 완료
- 실패 이유를 플레이어가 설명 가능
- 다음 콘텐츠에서도 같은 프레임을 재사용 가능
- 본편 흐름을 끊는 비용보다 얻는 경험 가치가 큼

이 기준은 BCP-2026-020의 `MINIGAME_NARRATIVE_FUNCTION_GATE`로 추출한다.

# C. 글쓰기

## C-1. 이번 주 핵심 변화와 근거

AI 글쓰기·프롬프트 작업의 핵심 개선점은 `더 긴 프롬프트`가 아니라 **정확한 컨텍스트 구조**다.

Base의 BCP-2026-004가 이미 Context Budget과 큐레이션 책임을 갖고 있으므로, 이번 보고서에서는 이를 새 규칙으로 만들지 않고 글쓰기·기획 프로젝트에 적용하는 쪽으로 정리한다.

## C-2. 현재 작업 방식의 개선점

프롬프트 컨텍스트를 다음처럼 분류한다.

| 등급 | 처리 |
|---|---|
| DIRECT | 현재 작업에 반드시 필요하므로 직접 포함 |
| REFERENCE | 필요할 때 찾아볼 경로·문서만 제공 |
| EXCLUDED | 현재 작업과 무관하므로 읽지 않음 |

장문의 프롬프트가 더 좋은 결과를 보장하지 않는다. 핵심은 **현재 결정에 필요한 정보 밀도**다.

## C-3. 직접 경쟁작·인접 장르·장르 밖 벤치마킹

원 보고서에서 검토한 사례:

- `Demon Lord: Just a Block`: 짧은 대사와 플레이어 주도 발견이라는 정보 절제.
- `Dread Neighbor`: 평범한 일상에 작은 이상을 삽입해 불안을 확대하는 구조.
- `WHAT-IF` 계열 연구: 분기 생성 자체보다 시작 상태·결정 지점·결과·재합류 구조를 관리하는 것이 중요하다는 참고점.

Base에 남길 글쓰기 질문:

> 한 장면에서 플레이어/독자가 실제로 기억해야 하는 정보는 무엇인가?

## C-4. 핵심 플레이어 또는 독자 경험

미스터리·괴담 글쓰기의 강한 경험 정의:

> 새 정보를 얻을 때마다 이전에 본 장면의 의미가 조금씩 달라진다.

즉 다음 사건만 궁금하게 하는 것이 아니라 **이미 본 정보를 다시 생각하게 만드는 것**이 핵심이다.

## C-5. 첫 장면의 인상

권장 구조:

```text
평범한 상황
→ 작은 모순
→ 누군가의 이상한 반응
→ 공식 설명
→ 공식 설명과 맞지 않는 사실
→ 독자/플레이어 질문
```

세계관 설명보다 질문을 먼저 만든다.

## C-6. 핵심 장면 진행 구조

모든 주요 장면에 다음을 기록할 수 있다.

```text
왜 이 장면이 존재하는가
누가 무엇을 원하는가
무슨 정보가 변하는가
무슨 감정이 변하는가
장면 뒤 무엇을 하고 싶어지는가
```

마지막 질문이 다음 플레이/다음 문단/다음 선택으로 연결되는 동력이다.

## C-7. 반복 피로도와 감정 곡선

에피소드마다 사건 이름만 바뀌고 정보 전달 방식이 같으면 반복감이 생긴다.

사건마다 `정보가 불완전한 이유`를 바꾸는 방식이 유효하다.

- 거짓말
- 기억 손실
- 기록 조작
- 관찰 오류
- 괴이 효과
- 의도적 은폐
- 사실은 정확하지만 해석이 틀림

## C-8. 선택과 결과, 보상 또는 정보 공개 구조

선택지는 성격 테스트보다 **정보를 어떻게 사용할지** 결정하게 만드는 편이 현재 프로젝트에 더 적합하다.

약한 예:

```text
믿는다 / 믿지 않는다
```

강한 예:

```text
진술을 근거로 현장을 폐쇄한다
진술을 보류하고 다른 기록을 먼저 확인한다
모순을 숨긴 채 추가 질문을 한다
```

선택이 실제 행동과 비용을 포함해야 한다.

## C-9. 온보딩·문장 가독성

권장 최소 원칙:

```text
한 대사 = 하나의 핵심 의도
한 장면 = 하나의 핵심 변화
한 선택 = 하나의 실제 비용
```

긴 대사가 필요할 수는 있지만, 행동 중 읽어야 하는 문장은 핵심 의도를 분리한다.

## C-10. 비주얼 아이덴티티·문체·상징

괴담 프로젝트에서는 문체 자체를 세 계층으로 분리할 수 있다.

| 문체 | 기능 |
|---|---|
| 생활 대화 | 현실감 |
| 공식 기록 | 권위와 신뢰의 외형 |
| 괴이 규칙 | 짧고 기억되는 공포 |

이 셋의 충돌이 작품 분위기를 만든다.

## C-11. 콘텐츠 제작 비용과 1인 제작 현실성

AI가 초안을 싸게 만들수록 콘텐츠 양을 늘리는 실수가 생길 수 있다.

생성 비용과 별개로 남는 비용:

- 설정 검수
- Canon 정합성
- 분기 테스트
- UI 줄바꿈
- 감정 연속성
- 복선 회수
- 번역
- 플레이 속도 검증

따라서 KPI는 생성량보다 **실제로 채택 가능한 장면 비율**에 가깝게 잡는 편이 낫다.

## C-12. 판매 포인트 또는 독자 유입 포인트

첫 장면의 정보량보다 **강한 질문**이 중요하다.

로그라인·상징·첫 모순이 동일한 핵심 질문을 가리키게 한다.

## C-13. 성공 요인과 실패·이탈 요인

성공 요인:

- 첫 장면에 질문 존재
- 정보 공개 후 이전 장면 재해석
- 캐릭터 욕망과 사건 정보가 충돌
- 선택이 실제 비용과 후속 변화를 만듦
- 장면 목적이 분명함

이탈 요인:

- 설정 설명이 사건보다 먼저 등장
- 모든 등장인물이 같은 방식으로 정보 전달
- 분기 수는 많지만 결과가 비슷함
- AI가 새 설정·새 분기를 계속 증식
- 복선 ID와 관리 구조가 독자 경험보다 복잡해짐

## C-14. 그대로 참고할 요소

- 짧고 기능적인 대사
- 환경·문서·UI를 서사 전달에 활용
- 한 장면의 핵심 질문을 제한
- 정보 공개 후 재해석 유도
- 분기의 시작 상태와 재합류 위치 관리

## C-15. 현재 프로젝트에 맞게 변형할 요소

- `urban-legend`: 조사 기록·공식 문서·현장 대사를 서로 다른 정보 신뢰도 계층으로 활용.
- `Coc-Fiction`: 게임식 첫 10분 Gate 대신 Canon·화자 정보 권한·장면 목적·퇴고 Discipline 사용.
- `Ten-Paces-Hidden-Moves`: 전투 전후 대사와 복기가 다음 무공 판단을 만들어야 함.
- `Blacksmith`: 결과 문구와 연대기가 숫자 반복이 아니라 작품의 기억을 강화.
- `omenward`: 전술 안내가 세계관 설명보다 현재 결정을 먼저 돕도록 구성.

## C-16. 도입하지 말아야 할 요소

- AI가 자유롭게 새 설정·분기·복선을 계속 추가
- 한 장면에서 여러 핵심 정보를 동시에 설명
- 기존 Canon/정본 owner를 우회하는 프롬프트
- 장면 목적 없이 분위기만 늘리는 대사
- 분기 수 자체를 품질 지표로 사용

## C-17. 작은 실험과 성공 기준

### 실험 C1 — 대사 30% 압축 비교

대표 장면 하나를 기존본과 압축본으로 비교한다.

성공 기준:

- 핵심 정보 손실 없음
- 핵심 질문 유지
- 감정 변화 유지
- 다음 행동 의도 유지
- 읽기 시간 감소

### 실험 C2 — 장면 목적 카드

대표 장면마다 다음 다섯 필드만 먼저 작성한다.

```yaml
scene_purpose:
character_want:
information_change:
emotional_change:
next_action_desire:
```

이 다섯 필드로 장면을 설명할 수 없으면 본문 집필 전에 구조를 재검토한다.

# D. 종합 반영안

## D-1. 세 영역 사이의 충돌과 시너지

바람직한 연결:

```text
글쓰기
→ 무엇이 문제인지 질문을 만든다

메인게임
→ 어떤 해결 방법을 선택할지 고민하게 한다

미니게임 또는 핵심 인터랙션
→ 그 판단을 직접 시험한다

결과
→ 성공·실패의 이유를 보여준다

다음 루프
→ 배운 내용을 이용해 새 판단을 한다
```

주요 충돌:

- 설명량 증가
- 시스템 증가
- QA 규칙 증가

세 가지가 동시에 일어나면 개발 시스템은 정교해져도 플레이어 경험은 복잡해질 수 있다.

## D-2. 이번 주 최우선 실행 제안

| 우선순위 | 작업 | 이유 |
|---|---|---|
| P0 | `PLAYER_EXPERIENCE_EVIDENCE_GATE` 정의 | 기술 PASS와 실제 경험 PASS의 공백 해소 |
| P0 | 대표 프로젝트 첫 10분 테스트 | 기능보다 이해·고민·결과 확인 |
| P1 | 핵심 화면을 Decision Screen 기준으로 감사 | 정보 과다와 버튼 목록화 방지 |
| P1 | 미니게임을 본편 기능 기준으로 재분류 | 제작비와 흐름 분산 방지 |
| P2 | BCP-2026-004 Context Budget의 프로젝트 적용 점검 | 프롬프트·문서 비대화 방지 |

## D-3. 추가하면 좋은 요소

새 대형 Skill보다 작은 계약을 선호한다.

- Player Experience Evidence
- First-10-Minutes Contract
- Decision-Screen Rule
- Minigame Narrative Function Gate

`Context Budget`은 기존 owner 재사용.

## D-4. 제거하거나 단순화할 요소

- 작업 전 전체 문서를 무조건 읽게 하는 프롬프트
- 동일 정보를 여러 문서에 중복
- 본편과 연결되지 않는 미니게임
- 첫 화면의 설명성 버튼·정보 과다
- 기술 PASS를 제품 PASS처럼 표현하는 문구
- 프로젝트마다 동일 목적의 별도 Skill 생성

## D-5. Base 승격 후보

### 승격 후보 A — `PLAYER_EXPERIENCE_EVIDENCE_GATE`

공용 가치: 매우 높음.

이유:

- 여러 프로젝트가 기술·UI 자동 검증을 강화하고 있음.
- 사람 사용성과 재미 검증이 자동으로 따라오지 않음.
- claim ceiling을 명확히 할 수 있음.

### 승격 후보 B — `FIRST_10_MINUTES_CONTRACT`

공용 가치: 높음.

주의:

- 정확한 10분을 장르 불문 강제하지 않음.
- 대표 문제·행동·선택·결과·다음 질문을 공용 골격으로 사용.

### 승격 후보 C — `DECISION_SCREEN_RULE`

공용 가치: 높음.

주의:

- 특정 레이아웃·UI 스타일을 강제하지 않음.
- 현재 결정의 정보 계층만 공용화.

### 승격 후보 D — `MINIGAME_NARRATIVE_FUNCTION_GATE`

공용 가치: 중~높음.

주의:

- 퍼즐·전투 자체가 메인 코어인 프로젝트에는 적용하지 않음.
- `CORE_INTERACTION_EVIDENCE` 예외 필요.

### 신규 승격 제외 — `Context Budget`

판정: 중복.

이미 BCP-2026-004가 책임을 갖고 있으므로 새 owner를 만들지 않는다.

# F. 벤치마킹 사용 규칙

이번 보고서에서 중요한 것은 작품 목록이 아니라 **벤치마크를 어떤 질문으로 변환할 것인가**다.

## 직접 경쟁작

검토 질문:

- 플레이어가 같은 핵심 고민을 하는가?
- 첫 10분에 무엇을 약속하는가?
- 실패·이탈 지점은 어디인가?

## 인접 장르

검토 질문:

- 현재 게임에 없는 감정 곡선이나 정보 구조를 제공하는가?
- 시스템 연결 방식에서 가져올 원리가 있는가?

## 장르 밖 참고작

검토 질문:

- UI 계층, 정보 절제, 상징, 반복 구조, 온보딩에서 가져올 원리가 있는가?

## 도입 판정

모든 벤치마크 결과를 다음 세 가지로 분리한다.

```yaml
COPY_AS_PRINCIPLE:
  # 원리 수준에서 거의 그대로 참고

ADAPT_TO_PROJECT:
  # 현재 프로젝트 코어 경험에 맞게 변형

DO_NOT_ADOPT:
  # 제작비·장르·플레이어 경험과 맞지 않아 제외
```

작품의 표면 기능을 그대로 복제하지 않는다.
